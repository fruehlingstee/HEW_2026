# DB実装前の具体案：配置・編集権限・削除

作成日: 2026-10-19。状態: 3方針の説明後、ユーザーの「理解した。次」を受け、本チャットの採用方針としてDBML・Prismaへ反映。4人合意・DB適用は未実施。

根拠: [未決事項DB-01〜DB-09](../plan/open-questions.md)、[4人レビュー](../memo/未決事項.md)、[関数契約](../plan/issue-reference/03-function-contracts.md)、[DB設計](../plan/issue-reference/04-database-design.md)。以下の「案」は採用時の検討内容として保持する。保存列・主なFKを反映した段階であり、Cookie認証・配置検証・削除処理の実装完了を意味しない。

## 1. 配置：最初は上面で移動・水平回転のみ

10月30日のPoCは5号土台と苺で検証する。上下移動・傾き・拡大縮小の操作は提供せず、以下の共通形式で保存する案。

| 項目 | 提案 | 理由 |
|---|---|---|
| 単位 | メートル。5号直径0.15、半径0.075 | 既存の座標契約案に合わせる |
| 原点 | ケーキ上面の中心を(0, 0, 0) | GLBとSVGで同じ基準を使う |
| 向き | Yが上、12時が-Z、3時が+X | 真上表示の左右・上下を固定する |
| 保存列 | pos_x / pos_y / pos_z / rot_y / scale | 担当資料の形式を採用し、DB資料のXYZ回転を修正する |
| 高さ | PoCではpos_y=0 | 上面に置く。GLBは接地面中心を原点とする |
| 回転 | rot_yのみ、ラジアン、0以上2π未満へ正規化 | 傾きの実装・製造指示を増やさない |
| 大きさ | PoCではscale=1 | 商品の実寸に合わせ、利用者が苺を拡大しない |
| 数値型 | PostgreSQL double precision（Prisma Float） | 3Dとの受渡しに使用。NaN・Infinityは保存前に拒否する |
| 配置番号 | 全置換保存の配列順に1〜N、入力seqNoもこの順番との一致を検証 | 保存後の3D・SVG・明細で同じ番号を使う |

編集中の削除・並べ替えでは番号の振り直しを許す。seqNoは永続的な配置IDとは扱わず、UIの選択状態には別の一時IDを使う。pending注文作成後は既存仕様どおり編集禁止となり、その時点の番号を注文明細へ固定する。保存の競合はDesignのversionで拒否する。

### はみ出し判定

苺モデルの上面投影を囲む円の半径を、モデルの実寸から③が測定する。サーバーにも同じ値が必要なので、partsに`footprint_radius_m`（正の実数、通常飾りで必須）を追加する案とする。任意の仮寸法はseedへ入れない。

判定は `sqrt(posX² + posZ²) + footprintRadius <= 0.075`。円で囲うため細長いパーツでは置ける範囲を狭めるが、水平回転しても端がはみ出ない判定にできる。モデル自体の厚みや接地位置は③の確認が必要。

この案は通常飾りのPoC用。苺同士・プレートとの重なり、外周デコの形・配置範囲・上限・プリセットは別途決める。DB-01全体や外周デコ仕様が解決したとは扱わない。

### 同じデータで確かめる例

SVGを150×150、中心(75, 75)、1単位=1mmとすると、`svgX=75+1000*posX`、`svgY=75+1000*posZ`とする。

| 場所 | posX | posY | posZ | SVG位置 |
|---|---:|---:|---:|---|
| 中心 | 0 | 0 | 0 | (75, 75) |
| 12時側 | 0 | 0 | -0.04 | (75, 35) |
| 3時側 | 0.04 | 0 | 0 | (115, 75) |

保存→再読込→3D→SVGで同じ配置となることを確認する。モデルの初期向きを-Zに統一する場合、右手系Y回転をSVGへ渡す角度は`-rotY*180/π`。円だけのSVGでは向きが見えないため、回転確認には向きの分かる印を使う。ここに記した例は受入条件であり、GLBでの実測結果ではない。

## 2. 共有：見るためのURLと、編集する権限を分ける

共有URLを知っている人は閲覧できるが、編集・注文開始・再共有の操作はできない案とする。

| 用途 | 提案 |
|---|---|
| 閲覧用 | 32バイト乱数のshareTokenをURLで渡し、DBにはSHA-256ハッシュのみ保持 |
| 編集用 | 通常利用者の専用セッションをHttpOnly Cookieで持ち、Designに所有セッションIDを保存 |
| 別端末 | 閲覧のみ。通常編集は作成したブラウザーに限る |
| Cookieを失った場合 | 元デザインの編集権限は復旧しない。再作成する |
| 注文後 | 所有者でも編集不可。期限切れ・取消後の再注文は既存方針どおり複製 |
| デモ | 既存demo_sessionsで認可し、通常用セッションと混同しない |

通常編集用に`design_edit_sessions`を追加する案。列はid、token_hash（一意）、created_at、expires_at、revoked_at。Designにnullableな`edit_session_id`を追加し、通常Designは必須、デモDesignではNULLとする条件を検討する。セッションIDだけで認可せず、Cookie秘密値のハッシュ・期限・失効を毎回検証する。

編集セッションの寿命は最終の認可済み編集から7日へ更新する案とし、閲覧だけでは延長しない。1ブラウザーで複数の通常Designを所有可能。セッションが有効でも、個々のDesignの保持期限・ロック・店舗所属を検査する。CookieはHttpOnly・SameSite=Lax・Path=/・Domainなし、HTTPSではSecure。変更操作にはOrigin確認を行う。

共有は明示操作で有効化する。Designに`share_token_hash`（nullable、一意）を追加し、停止はNULL化、再発行は新ハッシュへの置換で古いURLを無効化する。生トークンは発行時だけ返し、DBから復元しない。共有情報の失効時刻はDesignの保持期限に従い、未注文は最終更新+7日、注文後は受取日+30日。期限判定は清掃ジョブが遅れても行う。

公開DTOには店舗・表示用デザイン・配置・表示に必要なパーツ情報だけを明示選択する。所有セッション・トークンハッシュ・顧客情報・注文照会トークンは含めない。メッセージ文字列は共有内容に含むため、共有前に本人が内容を確認できるようにする。

### 確認するケース

- URLを受け取った別ブラウザーは閲覧できるが、保存・注文開始を拒否される。
- 所有者でもlocked_at設定後の保存は拒否される。
- 共有停止・再発行・保持期限超過後は古いURLを閲覧できない。
- Cookie削除後は編集不可。共有URLから編集Cookieを再発行しない。

別端末での編集・復旧が必要なら、この案を変更してから実装する。認証APIやCookie発行はまだ実装していない。

## 3. 削除：Design配下を消し、通常注文の財務履歴を残す

既存の保持期限と、orders.design_idのSET NULL・パレットのCASCADEは維持する。追加提案は以下。

| 対象 | 削除・参照の提案 |
|---|---|
| Design → Placement | CASCADE。保持期限後の座標削除を一括で行う |
| Design → Palette | 既存どおりCASCADE |
| Design → Order | 既存どおりSET NULL。金額・明細・決済は残す |
| Design → CapacityHold | design_idをnullableにし、FKはSET NULL。active中のNULLを禁止 |
| Part → Placement | RESTRICT。参照中パーツは削除不可 |
| Store → 業務データ | RESTRICT。店舗の停止は既存のis_activeで行う |
| 通常Order → 明細・履歴・決済・返金 | 自動連鎖削除を設けない。通常注文自体の物理削除は行わない |
| DemoSession → デモデータ | 全件CASCADEにはせず、認可したサービスが同一トランザクションで子から削除 |

この表は主な変更点。全FKの一覧レビューはDB-03で引き続き必要。通常注文に財務履歴を紐づけたまま、保持期限で個人情報と共有・座標を消す。

### 清掃の順番

1. 通常データでは店舗行→対象Design行の順にロックし、注文・仮確保作成と競合させる。デモは既存のdemo sessionロック契約に従う。
2. 未注文Designの削除は、更新から7日を過ぎ、注文がなく、有効なactive holdもないことをロック後に再確認する。期限切れholdは既存の解放処理を通す。
3. 注文済みDesignは受取日+30日を基準に削除し、orders.design_idと終端holdのdesign_idをNULLへする。active holdが残る異常状態は先に整合性を確認し、無条件に消さない。
4. 顧客情報・注文照会ハッシュをNULLへし、pii_erased_atを記録する。design_snapshot.messageTextなどの自由文も消去する。金額・税・決済ID・返金状態は保持する。
5. 同じ対象をもう一度処理しても成功するようにする。共有閲覧は期限切れを独立して拒否する。

active holdのdesign_id非NULL条件はCHECKで保証する案。外部決済の照合は残したorder_idとPaymentIntent IDを用い、期限後の成功決済は既存方針どおり注文を復活させず返金する。holdと注文の店舗・日付・Design一致はDB-04の保証方法と合わせて決める。

財務履歴の具体的な保存年数、状態履歴の自由文・通知・エラーの清掃範囲は未決のまま。無期限保持を確定したとは扱わない。

## 採用後の反映先と残る作業

ユーザーの採用と4人レビューを区別して記録し、以下を同時に更新する。

- DB-01: DBML、schema.prisma、担当資料、DB設計・ER図、配置入力契約。③④がモデル実寸と原点を確認する。
- DB-02: 編集セッション・共有列、認可条件、公開DTO、共有画面の仕様。デモとの分岐も確認する。
- DB-03: FK全件と清掃対象一覧、holdのNULL条件、通常注文・デモの削除手順。

この3方針を反映しても、DB-04〜DB-09と外周デコの保留事項は残る。初回migrationの作成・適用や#27の完了を自動的に許可するものではない。

反映時の補足: 編集セッションは参照中のDesignが残る間はRESTRICTとし、失効・期限切れで編集を拒否する。先にDesignを清掃し、参照がなくなったセッションを後で削除する。座標の有限値・回転範囲・正の倍率はCHECKの設計として記録した。苺PoCのposY=0・scale=1と通常飾りの範囲照合は今後の入力検証で実装する。外周デコを含む全配置へPoC専用制約を勝手に拡大しない。
