# 業務ロジック

実装時の判断基準をまとめる。型と関数は [03-function-contracts.md](./03-function-contracts.md)、保存先は [04-database-design.md](./04-database-design.md) を参照する。

## 商品・デザイン

- 1 注文 = 5号ケーキ 1 台。
- 外周デコの料金はケーキ本体価格に含めず、白を含む各デコの使用個数に応じて「単価 × 個数」を加算する。1個あたり20円（税抜）とする。配置プリセットを約3種類用意し、プリセット選択と自由配置の両方に対応する。プリセットも構成するデコの個数に基づいて料金を計算し、白以外の使用色数に応じた色変更料金を別途加算する。
- 外周デコレーションはVer1.0で提供する。「あり・なし」を選択可能とし、自由配置・色変更に対応する。色変更には追加料金が発生する。形は保留。プリセット内容などの未決事項は `../open-questions.md` のD-2を参照する。
- スポンジ色・クリーム色は自由度を優先する。
  - Ver0.5: 用意した色候補から選択。
  - Ver1.0: HTML color picker で指定し `#RRGGBB` 保存。
- メッセージプレートを採用する。
- 登録済み装飾パーツは常に利用可能。個別在庫は管理しない。
- パーツの種類・最大配置数は後から変更できるよう、UI 定数とバリデーションを一か所に集約する。
- pending注文作成と同一トランザクションでデザインをロックし、色・メッセージ・配置・パレットを変更不可にする。支払い再試行は有効なholdとpending注文がある間は同じ注文で行う。期限切れ・キャンセル後の再注文や内容変更は新しいデザインへ複製し、金額・枠・アレルゲンを再確認する。
- 画像印刷は 2027-01-15 に採否判断。それまではスコープ外。

## 価格・税

通常飾りと外周デコは同じplacementsへ保存し、parts.kindで区別する。外周デコの色はplacements.colorに正規化した色コードを保存する。design_palette_colorsは再利用用であり、料金集計の対象ではない。パレットの変更・削除では既存配置の色を変えない。

外周デコの色変更料金は、ケーキ1台で実際に使用する標準色以外の色数 × 50円（税抜）とする。標準色は白とし、白には色変更の追加料金を課さない。同じ色を何個に使っても1色分とし、その色のデコをすべて削除した場合は加算を取り消す。作成した色をパレットに登録し、各デコで再利用できるようにする。未使用のパレット色は課金対象に含めない。

白以外1色につき50円（税抜）で確定。以下の計算式に、外周デコの個数課金と色変更料金を含める。外周デコは1個20円（税抜）とする。通常の飾りと外周デコを分けて集計し、同じデコを二重計上しない。

初期値:

| 項目 | 金額 |
|---|---:|
| 5号ケーキ本体 | 3,500円 |
| メッセージプレート | 300円 |
| 外周デコ本体 | 20円/個（税抜・確定） |
| 外周デコの色変更（白以外） | 50円/色（税抜・確定） |
| 苺・ラズベリー等 | パーツ完成後に確定 |
| 消費税 | 8% |

```text
colorSurcharge = 外周デコで実際に使用する白以外の色数 × 50
decorationPrice = 外周デコの使用個数 × 20
subtotal = basePrice + platePrice + Σ(通常の飾り単価 × 個数) + decorationPrice + colorSurcharge
tax      = floor(subtotal × 0.08)
total    = subtotal + tax
```

pending注文作成時に全明細・単価・税率・合計と製造内容のスナップショットを保存する。保存先と配置番号の対応はDB設計の「注文内容を固定する契約」に従う。確認画面から金額・アレルゲン等が変わった場合は注文を作らず再確認へ戻す。後日の価格変更や決済成功Webhookで既存注文の内容を再計算・上書きしない。

## アレルゲン

- 絞り込み機能、リアルタイム警告、複雑な同意画面は作らない。
- 実際に選んだパーツに関係するアレルゲンだけを重複除去して表示する。
- 表示場所は注文最終確認と店舗用指示書。
- 確認操作時に `allergen_confirmed_at` を記録する。
- 表示文例: 「表示内容は使用予定の材料に基づく参考情報です。重篤なアレルギーがある場合は注文前に店舗へご確認ください。」

## 受取可能日・容量

- 5号ケーキ 1台 = 1 point。
- 初期の 1 日上限 = 5 points。
- 曜日別の通常上限を日別設定で上書きできる。
- 店休日は `is_closed` を優先し空き 0 とする。
- 受取日判定は JST、保存日時は UTC。
- 決済開始前に 15 分の仮押さえを作る。
- 期限切れ仮押さえは空き照会時・注文作成時に解放する。

```text
available = effectiveCapacity
          - usedOrderPoints
          - activeUnexpiredHoldPoints
```

usedOrderPointsは非デモのconfirmed / in_production / ready / completed注文のpoint合計。confirmed holdを別加算しない。Ver1.0は店舗行をロックして空き再計算と確保を直列化し、最後の1枠を複数人へ売らない。期限判定はロック取得後のDB時刻を使用し、expires_atと同時刻は期限切れとする。

## 注文と受取番号

表示番号は `MMDD-3桁連番`。連番は店舗・受取日ごとに 001 から採番する。

```text
pending
  ├─ confirmed → in_production → ready → completed
  ├─ expired
  ├─ cancelled
  └─ rejected
```

- `pending`: 仮押さえ中・決済待ち。
- `confirmed`: Webhook で決済成功を確認済み。
- `in_production`: 店舗が製造開始。
- `ready`: 受取可能。
- `completed`: 引き渡し済み。
- `expired`: 15 分超過等で注文不成立。
- `cancelled`: 顧客または店舗都合のキャンセル。
- `rejected`: 製造不能など店舗判断。

状態変更時は必ず履歴と操作者を記録する。

## ゲスト注文照会

- 注文作成時に 32 byte 以上の秘密トークンを 1 回だけ発行する。
- DB にはハッシュのみ保存する。
- メールの専用リンクから注文詳細・許可されたキャンセル操作へ進む。
- エラー文で注文の存在有無を推測できないようにする。
- トークン/IP 相当キーにレート制限を適用し、生値は保存しない。

## Stripe 決済

1. pending注文と有効holdを確認し、DBに作成予定paymentと固定冪等キーを保存する。コミット後にPaymentIntentを作り、同じ注文の支払い再試行では再利用する。
2. クライアント表示だけで注文をconfirmedにしない。
3. 署名検証済みWebhookをreceivedとして永続化してから応答する。DBから未処理・失敗イベントを再実行する。
4. 店舗ロック下で期限・現在状態・決済の対応と金額を再確認し、payment更新・order確定・hold確定・履歴・通知予約・event完了を同じトランザクションで保存する。
5. 期限後・取消後の成功は注文を復活させず、全額返金要求を保存する。外部APIはコミット後に実行し、失敗・結果不明を照合して復旧する。
6. 重複はprocessedなら反映済み結果を返し、received / failedなら処理を続行する。別event IDでも同じpaymentの成功を二重反映しない。

詳細な状態分岐・ロック順・再実行・受入条件は[競合処理](09-capacity-payment-concurrency.md)を参照する。

## キャンセル・返金

具体的な率は店舗合意で設定できるようポリシー定数にする。判定順は固定する。

| 条件 | 処理 |
|---|---|
| 未決済 / pending | hold を解放し expired または cancelled。返金なし |
| 期限切れ・取消後に決済成功 | 注文を復活させず全額返金。空き枠が残っていても同じ扱い |
| 支払済み・規定期限より前 | ポリシーの返金率を適用 |
| 製造開始後または期限超過 | 原則返金なし。店舗判断を理由付きで記録 |
| Stripe 返金済み | 再実行せず既存結果を返す |

```text
refundableAmount = floor(paidAmount × refundRateBps / 10000)
feeBasis         = paidAmount - succeededRefundAmount
platformFee      = floor(feeBasis × platformFeeRateBps / 10000)
```

返金判断と実行結果を別々に保存する。Stripe 返金には一意な冪等キーを使用する。

## メール

注文受付、決済確定、受取可能、キャンセル等を Resend で通知する。送信失敗で注文本体を巻き戻さない。dedupe key、試行回数、最終エラーを保存し再送する。

## デモ・障害時

- デモモードは決済、個人情報、本番容量を使わない。
- 展示は PC 1 台 + モニター 2 台を想定する。
- 3D が失敗したら SVG 上面図・静止画・事前録画の順でフォールバックする。
- 通信障害時も説明できるデモデータと手順書を準備する。

## 保持・清掃

- 未注文デザイン: 最終更新から 7 日。
- 注文済みデザイン: 受取日から 30 日。
- 期限後は個人情報・配置・共有トークンを削除または匿名化する。
- 会計・監査に必要な金額、決済、返金、状態履歴は保持する。
- 清掃処理は何度実行しても安全で、件数と失敗理由を記録する。
