# 業務ロジック

実装時の判断基準をまとめる。型と関数は [03-function-contracts.md](./03-function-contracts.md)、保存先は [04-database-design.md](./04-database-design.md) を参照する。

## 商品・デザイン

- 1 注文 = 5号ケーキ 1 台。
- 外周デコレーションは扱わない。
- スポンジ色・クリーム色は自由度を優先する。
  - Ver0.5: 用意した色候補から選択。
  - Ver1.0: HTML color picker で指定し `#RRGGBB` 保存。
- メッセージプレートを採用する。
- 登録済み装飾パーツは常に利用可能。個別在庫は管理しない。
- パーツの種類・最大配置数は後から変更できるよう、UI 定数とバリデーションを一か所に集約する。
- 注文作成後のデザインはロックし、変更時は複製して新しいデザインを作る。
- 画像印刷は 2027-01-15 に採否判断。それまではスコープ外。

## 価格・税

初期値:

| 項目 | 金額 |
|---|---:|
| 5号ケーキ本体 | 3,500円 |
| メッセージプレート | 300円 |
| 苺・ラズベリー等 | パーツ完成後に確定 |
| 消費税 | 8% |

```text
subtotal = basePrice + platePrice + Σ(unitPrice × quantity)
tax      = floor(subtotal × 0.08)
total    = subtotal + tax
```

注文作成時に全明細・単価・税率・合計を保存する。後日の価格変更は既存注文へ反映しない。

## アレルゲン

- 絞り込み機能、リアルタイム警告、複雑な同意画面は作らない。
- 実際に選んだパーツに関係するアレルゲンだけを重複除去して表示する。
- 表示場所は注文最終確認と店舗用指示書。
- 確認操作時に `allergen_confirmed_at` を記録する。
- 表示文例: 「表示内容は使用予定の材料に基づく参考情報です。重篤なアレルギーがある場合は注文前に店舗へご確認ください。」

## 受取可能日・容量

- 5号ケーキ 1台 = 1 point。
- 初期の 1 日上限 = 5 points。
- 曜日別の通常上限を日別設定で上書きできる。
- 店休日は `is_closed` を優先し空き 0 とする。
- 受取日判定は JST、保存日時は UTC。
- 決済開始前に 15 分の仮押さえを作る。
- 期限切れ仮押さえは空き照会時・注文作成時に解放する。

```text
available = effectiveCapacity
          - confirmedOrderPoints
          - activeUnexpiredHoldPoints
```

仮押さえ作成は店舗・日付単位のトランザクションで直列化し、最後の 1 枠を複数人へ売らない。

## 注文と受取番号

表示番号は `MMDD-3桁連番`。連番は店舗・受取日ごとに 001 から採番する。

```text
pending
  ├─ confirmed → in_production → ready → completed
  ├─ expired
  ├─ cancelled
  └─ rejected
```

- `pending`: 仮押さえ中・決済待ち。
- `confirmed`: Webhook で決済成功を確認済み。
- `in_production`: 店舗が製造開始。
- `ready`: 受取可能。
- `completed`: 引き渡し済み。
- `expired`: 15 分超過等で注文不成立。
- `cancelled`: 顧客または店舗都合のキャンセル。
- `rejected`: 製造不能など店舗判断。

状態変更時は必ず履歴と操作者を記録する。

## ゲスト注文照会

- 注文作成時に 32 byte 以上の秘密トークンを 1 回だけ発行する。
- DB にはハッシュのみ保存する。
- メールの専用リンクから注文詳細・許可されたキャンセル操作へ進む。
- エラー文で注文の存在有無を推測できないようにする。
- トークン/IP 相当キーにレート制限を適用し、生値は保存しない。

## Stripe 決済

1. pending 注文と有効 hold を確認する。
2. 注文 ID を metadata に入れた PaymentIntent を作る。
3. クライアント表示だけで注文を confirmed にしない。
4. 署名検証済み Webhook を受け、event ID の重複を確認する。
5. DB トランザクションで payment 更新、order 確定、hold 確定、履歴追加を行う。
6. 重複 Webhook は成功応答して何も変更しない。

## キャンセル・返金

具体的な率は店舗合意で設定できるようポリシー定数にする。判定順は固定する。

| 条件 | 処理 |
|---|---|
| 未決済 / pending | hold を解放し expired または cancelled。返金なし |
| 支払済み・規定期限より前 | ポリシーの返金率を適用 |
| 製造開始後または期限超過 | 原則返金なし。店舗判断を理由付きで記録 |
| Stripe 返金済み | 再実行せず既存結果を返す |

```text
refundableAmount = floor(paidAmount × refundRateBps / 10000)
feeBasis         = paidAmount - succeededRefundAmount
platformFee      = floor(feeBasis × platformFeeRateBps / 10000)
```

返金判断と実行結果を別々に保存する。Stripe 返金には一意な冪等キーを使用する。

## メール

注文受付、決済確定、受取可能、キャンセル等を Resend で通知する。送信失敗で注文本体を巻き戻さない。dedupe key、試行回数、最終エラーを保存し再送する。

## デモ・障害時

- デモモードは決済、個人情報、本番容量を使わない。
- 展示は PC 1 台 + モニター 2 台を想定する。
- 3D が失敗したら SVG 上面図・静止画・事前録画の順でフォールバックする。
- 通信障害時も説明できるデモデータと手順書を準備する。

## 保持・清掃

- 未注文デザイン: 最終更新から 7 日。
- 注文済みデザイン: 受取日から 30 日。
- 期限後は個人情報・配置・共有トークンを削除または匿名化する。
- 会計・監査に必要な金額、決済、返金、状態履歴は保持する。
- 清掃処理は何度実行しても安全で、件数と失敗理由を記録する。
