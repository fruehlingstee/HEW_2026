## 1. 概要

CakeCanvasは、利用者が5号・6号ケーキのスポンジ・クリームの色を指定し、3Dプレビュー上で飾りを自由に配置できるセミオーダーケーキサービスである。

ゼロから作る方法に加え、他の利用者が公開した人気デザインを探し、自分用にコピーして色・飾り・メッセージを変更できる。会員はマイページでデザイン・お気に入り・注文履歴を管理し、気に入った構成を再編集・再注文できる。公開は作者の明示操作で行い、注文しただけでは公開しない。

注文情報から店舗向けの番号付き俯瞰配置図と製造指示書を生成し、予約枠、Stripeテスト決済、店頭受取までを扱う。ケーキ店へのSaaS提供を想定し、Ver1.0は1店舗・1注文1台（5号または6号）・店頭受取のみとする。マルチテナントはDB設計のみ対応し、画面・デモは1店舗固定とする。

## 2. 背景・課題

- 電話・店頭・LINEでの曖昧な注文は、完成イメージの齟齬、聞き漏らし、価格の不透明さにつながる。
- 店舗は聞き取り・見積もり・仕様記録に時間を取られる。
- 買い手は自分でデザインした体験を求めるが、フルオーダーは高価で敷居が高い。
- 自由に作れるだけでは完成形を思い描きにくい利用者に、公開作品を出発点とする作成方法を用意する。
- 過去の自作やお気に入りを保存し、次の記念日に再利用できるようにする。

これらは現時点では仮説。

## 3. ターゲット

| 区分 | 対象 |
|---|---|
| 買い手 | 誕生日・記念日に贈る個人、主に10〜30代、推し活需要 |
| 顧客(課金対象) | オーダー対応の工数を減らしたい個人経営〜中規模のケーキ店 |

直接の顧客はケーキ店であり、買い手は店舗の顧客である。

## 4. 提供価値

- 買い手: 3Dで完成形を確認し、自作または人気作品のコピーから飾り付けできる。価格・関連アレルゲンを確認し、会員はデザイン・お気に入り・注文履歴を再利用できる。
- 店舗: 注文仕様が確定し、配置図つき製造指示書・予約枠・決済を一体で管理できる。
- 同じ配置データを3Dプレビューと製造指示書で共用することが中核となる。

## 5. 主要機能

### 買い手側

1. 5号（直径15cm）または6号（直径18cm）を選び、スポンジ・クリームの色を指定する。Ver0.5はプリセット3色、Ver1.0はカラーピッカー。色は `#RRGGBB` で保存する。
2. フルーツ・チョコ・飾りを3D上でドラッグ配置し、回転・俯瞰で確認する。飾りは個数課金とし、上限は種類別にフルーツ・スイーツ・ミント20個、絞りクリーム32個、お祝いの飾り10個とする。種類・上限は後から変更できる設計にする。
3. メッセージプレートは300円(税抜)、20文字、1行、書体1種類。改行・絵文字・機種依存文字は許可しない。
4. 注文確認画面で関連アレルゲン・店舗注記を表示し、確認時刻を保存する。
5. 日単位で受取日を選び、事前決済・即時キャプチャをStripeテストモードで行う。店頭受取番号を発行する。
6. 会員注文とゲスト注文に対応する。会員は自分の注文履歴、ゲストは秘密トークン付きURLから、注文内容・受取番号・状態の照会、キャンセル申請、返金状況確認を行う。既存の注文受付後画面はPC・スマホ対応を維持する。注文手続きはPCで行い、確定済み注文の内容は編集できない。元の保存デザインの再編集は既存注文へ影響させない。
7. ステータスと日時から返金率を判定し、申請・返金結果・通知を記録する。
8. 展示では共有URLを表示・コピーできるようにし、PCで構成データを再描画して完成画像を保存できるようにする。
9. メール・パスワードによる会員登録、メール確認、ログイン・ログアウト、パスワード再設定、プロフィール変更、退会を提供する。
10. 会員のマイページに、保存したデザイン、自分の公開作品、お気に入り、注文履歴を表示する。
11. 公開ギャラリーで作品を閲覧し、新着順・人気順に並べる。人気順は同じ店舗の公開中作品のお気に入り数を基準とする。
12. 会員は公開作品をお気に入りに登録できる。1会員につき同じ公開版への登録は1件とする。
13. 公開中かつコピーを許可した作品から、色・飾り・配置を新しい自分のデザインへコピーして編集する。価格・提供可能なパーツ・アレルゲンは現在の店舗情報で再確認する。
14. 会員は自分のデザインにタイトル・説明・公開用表示名を付けて公開し、コピー可否を設定できる。公開を取り下げた場合は新規閲覧・コピーを停止し、既存のコピーや注文内容は保持する。

外周デコはVer1.0で提供し、「なし」または形を1つ選んで、ケーキの縁に一周付ける。料金は0円とし、店舗の商品マスタで価格・提供可否を変えられるようにする。形の種類と、3Dプレビュー・製造指示書・保存データへの反映方法は設計時に決定する。

上に置く絞りクリームの飾りは1個20円（税抜）とし、白以外の色を使った場合は、使った色の数 × 50円（税抜）を加算する（2026-09-14に外周デコ向けに決めた料金を、2026-11-26に絞りクリームの飾りへ移した）。

配送、手書きメッセージ、SNSログインは現行スコープ外とする。画像印刷は2027-01-15に条件付きで採否を再判定する。新規の会員・マイページ・ギャラリー画面のスマホ対応範囲は別途決定し、既存のPC編集・注文受付後のPC／スマホ対応を拡張済みとは扱わない。

### 店舗側

1. パーツの登録・価格・アレルゲン・新規利用の有効／無効を管理する。`parts.is_active` で新規利用を制御し、無効化しても過去の公開・注文スナップショットは維持する。在庫数の管理は行わない。
2. 製造ポイント制の日次キャパ、臨時休業、リードタイムを管理する。
3. 注文一覧・詳細・進捗更新を行う。不適切な注文を却下でき、店舗都合のキャンセルは100%返金する。
4. A4縦1枚の製造指示書を出力する。
5. 会員アカウントと店舗所属・権限を使ってスタッフ本人を識別し、管理画面・各操作を制御する。店舗共通のパスワードは持たない。
6. Stripe返金失敗を確認し、店舗画面から再実行できるようにする。

### 5-A. アレルゲン

店舗が登録した原材料情報に基づく参考情報として提供し、最終確認は店舗が行う。実際に関係する品目を注文確認画面と製造指示書に表示する。

```text
allergens       (id, code, name, category, display_order)
part_allergens  (part_id, allergen_id, contains_type: contains | may_contain)
stores          (..., contamination_note)
```

選択パーツのアレルゲンを集計し、同一品目の `contains` と `may_contain` が競合する場合は `contains` を優先する。「含む」と「同一設備」を区別する。

上記の区分・店舗注記は維持する要件だが、統合DB案v4の `allergens` / `part_allergens` / `stores` には一部の列が未収録である。DB案だけから実装せず、区分と注記の保存先を[補完事項](db-v4-project-revision.md#db案v4の補完事項)として確認する。

初期マスタは卵・乳・小麦と、採用するチョコレート等に実際に関係する品目から開始する。

除外フィルタ、追加前警告、28品目を分類する複雑なUIは実装しない。アレルゲンの最終確認時刻は `orders.allergen_confirmed_at`、注文時の表示内容は `order_design_snapshots.allergen_snapshot` に保存する。会員規約等への同意は別用途の `user_consents` に記録する。

注意書き:
「表示内容は店舗が登録した原材料情報に基づく参考情報です。同一設備で卵・乳・小麦を含む製品を製造しています。重篤なアレルギーをお持ちの方は注文前に店舗へご相談ください。」

### 5-B. 注文・予約枠

5号1台を1製造ポイント、初期日次上限を5ポイントとする。受取枠は日単位で、時間帯別管理と飾り数のポイント加算は行わない。

```text
store_weekly_capacity (store_id, weekday, capacity_points)
daily_capacity       (store_id, pickup_date, capacity_points, is_closed)
capacity_holds       (order_id, store_id, pickup_date, points, status, expires_at)
```

曜日別デフォルトを持ち、日付レコードは注文時にupsertする。繁忙期の上限上書きと臨時休業を設定できる。受取可能日の判定はAsia/Tokyoで行う。

最短3日前までの受付、受付上限日数、締切時刻の業務要件は維持する。これらの設定列は統合DB案v4に未収録のため、店舗設定の保存先を実装前に補完する。予約使用量は有効な仮確保と確定枠から集計し、別カウンターと二重管理しない。

- 決済開始時に枠を15分間仮確保する。予約枠の確認・更新はトランザクションと行ロックで保護し、過剰予約を防ぐ。
- 枠不足なら決済を開始しない。
- `payment_intent.succeeded` Webhookを根拠に注文確定する。仮確保分を確定時に二重消費しない。
- 期限切れは空き枠確認時にも解放し、Cronだけに依存しない。
- 注文作成・決済試行・返金要求ごとに冪等性キーを持ち、同じ要求の再送では同じキーを使う。別の正規な決済試行を、同一注文だからという理由で遮断しない。
- 期限切れと決済成功が競合した場合の処理は、DB・決済設計時に①②で明文化する。

通常の状態遷移は `pending → confirmed → in_production → ready → completed`。例外は `cancelled`、`rejected`、`expired`。全遷移を `order_status_logs` に記録する。

店舗UIでは月カレンダーと残枠(例:残3/5pt)を表示し、日別キャパ・休業を編集する。満枠日は買い手側の日付選択を無効にする。

### 5-C. デザイン・製造指示書

```text
designs                (id, user_id, forked_from_publication_id, version, ...)
placements             (id, design_id, part_id, position_x/y/z, rotation_x/y/z, scale, seq_no, color)
orders                 (id, user_id, source_design_id, ...)
order_design_snapshots (order_id, schema_version, configuration, allergen_snapshot, captured_at)
order_items            (order_id, line_no, kind, name_snapshot, unit_price_excl_tax, quantity, line_total_excl_tax)
```

- 編集用の `designs` と `placements` は更新可能な構成データとして保持する。会員は自分のデザインを保存・再編集できる。
- `orders.source_design_id` は元デザインへの参照とし、一意にしない。同じデザインから再注文できる。
- 注文・決済対象を作る時点で、色・文字・全配置・パーツと資産バージョンを `order_design_snapshots.configuration`、名称・単価・数量を `order_items` へ確定保存する。金額と構成は同じトランザクションで固定し、以後のマスタ変更や元デザインの再編集を反映しない。
- 決済開始後に内容を変える場合は、既存の決済対象を書き換えず、再見積もりと新しい注文操作として扱う。二重決済や枠の重複確保を防ぐ手順は実装契約で定める。
- 会員の保存デザインに旧来の「未注文7日」を一律適用しない。ゲストの未注文デザインは7日を初期方針とし、会員保存・公開版・注文スナップショットの保持と退会時の扱いは別に定義する。注文連絡先の匿名化は受取日の30日後とする。
- 編集画面は `placements`、注文後の3D・SVG・製造指示書は確定スナップショットを読む。どちらも同じ座標契約を使い、`(x, z)` を真上に投影する。`seq_no` を飾り明細と対応させる。
- 3D参考画像は印刷時にブラウザで生成し、サーバーに保存しない。失敗時もSVGだけで指示書を成立させる。

出力はA4縦1枚、ブラウザの印刷CSS(`@media print`)でPDF化する。記載順は以下とする。

1. 注文番号・受取番号・受取日・店舗名・印刷日時
2. 氏名・電話番号
3. 5号ケーキの仕様、スポンジ・クリームの色見本、実物との色差に関する注記
4. 番号付きの飾り明細(パーツ名・個数)
5. 番号付き俯瞰配置図、12時方向の基準線、直径mmのスケール
6. メッセージ原稿・書体・文字数
7. アレルゲン(含む/同一設備)・店舗注記
8. 備考
9. 製造完了・検品・引き渡しのチェック欄

SVGは白背景のベクタ図として印刷時の読みやすさを優先し、3D縮退時も共用する。

### 5-D. 認証・注文照会・個人情報

会員はログイン状態と `orders.user_id` による本人確認で自分の注文を照会する。ゲスト照会URLは `/orders/{order_no}?t={token}` とし、ランダム32バイトのトークンを発行して `order_access_tokens.token_hash` にSHA-256ハッシュを保存する。有効期限は受取日+30日。受取番号をWeb認証に使用しない。

- 受取番号: `MMDD-日別3桁連番` (例: `0907-023`)。店舗・受取日・連番の組み合わせを一意にする。
- 店頭照合: 下3桁と氏名または電話番号下4桁。
- 照会: トークン単位で15分30回。
- キャンセル: 確認画面を経由し、ゲストはトークンとIP単位で15分5回。会員も本人確認と回数制限を適用する。冪等性キー・状態確認・返金上限確認で二重実行を防ぐ。
- IPはハッシュ化し、制限超過時はHTTP 429。
- 本注文では氏名・電話番号・メールアドレスを `order_contacts` に保存する。会員プロフィールを初期入力に使えるが、後の変更を過去注文へ反映しない。住所・フリガナは取得しない。
- 受取日の30日後に注文連絡先と関連通知の個人情報を匿名化・破棄する。金額・決済・返金履歴は分離して保持する。会員プロフィールの保持期限とは分ける。

店舗スタッフも `users` を使って本人を識別し、`store_memberships` の店舗所属・`owner / manager / staff` により管理操作を制御する。認証は会員と共通化し、店舗共通パスワードを `stores` に置く旧方式は廃止する。管理画面の全ルートと各データ操作で、ログイン状態・有効な所属・対象店舗・権限を確認する。認証ライブラリの採否と依存関係追加は実装時に別途確認する。

### 5-E. 会員登録・マイページ

- メール・パスワードで登録し、メール確認後に有効会員とする。重複メールの照合には正規化した `users.email_key` を使う。
- アカウントは `users`、ニックネーム・既定連絡先は `user_profiles`、パスワードのハッシュは `password_credentials`、ログイン状態は `auth_sessions` に分離する。
- メール確認・パスワード再設定は `auth_action_tokens` で用途・有効期限・使用済み状態を管理する。ログアウト・パスワード再設定・利用停止・退会時に必要なセッション失効を行う。
- 利用規約等の文書種別・版・同意日時は `user_consents` に保存する。注文時のアレルゲン確認と混同しない。
- マイページでは、保存デザイン・自分の公開作品・お気に入り・自分の注文を表示する。プロフィールの本名・電話番号を公開作品に出さない。
- ゲスト注文は残す。既存のゲスト注文を会員へ紐づける場合は、メール一致だけで紐づけず注文の操作権限を確認する。
- 退会時はログイン・操作権限を失効させ、プロフィール等を匿名化・削除する。注文・決済・監査履歴は別の保持方針で残す。

### 5-F. 公開ギャラリー・人気作品からのコピー

- 一般公開する構成は `design_publications.configuration` に固定保存し、元の編集デザインとは分離する。公開内容を変更する場合は新しい公開版を作る。
- ギャラリーの閲覧はゲストにも許可する。公開・お気に入り・永続的なコピー保存は、本人確認済みの有効会員向けを初期方針とする。
- 人気順は、同じ店舗の公開中作品に対する `design_likes` の件数で判定する。同数なら公開日時・IDで順序を安定させる。新着順も提供する。閲覧数や注文数によるランキングは初期実装に含めない。
- コピー元が公開中かつ `allow_remix = true` であることを確認し、新しい `designs`・`placements` を本人所有で作成する。コピー元は `designs.forked_from_publication_id` へ記録する。
- コピー後は色・飾り・配置・メッセージを編集できる。元の作者の編集データや注文情報は変更しない。価格・有効パーツ・アレルゲンはコピー時と注文時に現在の店舗条件で検証する。
- 公開は明示的な操作とし、注文や保存だけでは公開しない。タイトル・説明・表示名・構成の公開内容を確認し、実名を含むメッセージ等は公開前に変更・除去できるようにする。
- 作者による非公開化後は一覧・公開API・新規コピーを止める。すでに作成された他会員のコピーや注文を連鎖削除しない。作者退会時の公開停止とクレジット表示も保持方針に含める。

## 7. お金の流れ

### 価格計算(プロジェクト仕様)

絞りクリームの飾りの色変更料金は、ケーキ1台で実際に使用する標準色以外の色数 × 50円（税抜）とする。標準色は白とし、白には色変更の追加料金を課さない。同じ色を何個に使っても1色分とし、その色の飾りをすべて削除した場合は加算を取り消す。作成した色をパレットに登録し、各飾りで再利用できるようにする。未使用のパレット色は課金対象に含めない。

外周デコは、形を1つ選ぶ方式で0円とする（2026-11-26決定）。絞りクリームの飾りは1個20円（税抜）で、以下の「飾り料金」に含める。

```text
ベース価格   = 5号 2,500円 / 6号 3,000円
飾り料金     = 置いた飾りの単価の合計（絞りクリームの飾りは1個20円）
色変更料金   = 絞りクリームの飾りで実際に使用する白以外の色数 × 50円
外周デコ料金 = 0円（形を1つ選ぶ）
小計   = ベース価格 + 飾り料金 + メッセージプレート料金 + 色変更料金 + 外周デコ料金
消費税 = floor(小計 × 0.08)
合計   = 小計 + 消費税
```

スポンジ・クリームの色指定は0円。金額は整数円で保存し、税は小計に対して1回だけ計算・端数切り捨てとする。

| 項目 | 税抜仮価格 |
|---|---:|
| 5号ケーキ（直径15cm） | 2,500円 |
| 6号ケーキ（直径18cm） | 3,000円 |
| スポンジ・クリームの色指定 | 0円 |
| 外周デコ（形を1つ選ぶ） | 0円 |
| 絞りクリームの飾り | 20円/個 |
| 絞りクリームの色変更（白以外） | 50円/色 |
| メッセージプレート | 300円 |
| 苺 | 200円 |
| ラズベリー | 120円 |
| ブルーベリー | 80円 |
| チョコプレート | 150円 |

絞りクリームの飾りは1個20円、色変更は白以外1色につき50円（いずれも税抜）とする。外周デコは0円とする（2026-11-26決定）。それ以外の価格は初期実装用の仮値で、コア完成後に見直す。

### 返金規定(ステータス×日時)

| 条件 | 返金率 |
|---|---:|
| 受取日の3日前まで、製造未着手 | 100% |
| 上記以外で前日23:59まで、製造未着手 | 50% |
| 製造中以降 | 0% |
| 当日・無連絡 | 0% |
| 店舗都合 | 時期を問わず100% |

50%返金は税込総額の50%を端数切り捨てで算出する。返金不可でも申請を残す。Stripe返金失敗は `failed` として記録し、店舗画面から再実行できるようにする。

SaaS収益モデルの月額5,000円は例示。プラットフォーム手数料は返金後に店舗へ残る金額の3%とする。店舗向け月次サマリ(売上・返金・手数料)は旧企画のVer1.5項目であり、着手時にコア完成状況と優先順位を確認する。実際の決済はStripeテストモードとする。

注文関連のメールは注文受付・受取可・購入者キャンセル・店舗却下/返金の4種類。送信結果をDBへ記録し、同一メールを二重送信しない。

会員機能の追加に伴い、上記の注文通知にメール確認・パスワード再設定の通知を加える。`email_deliveries` で注文または会員に関連付けて送信結果を管理し、認証用の生トークンは送信ログに保存しない。返金率・判定根拠の記録や返金不可申請の保存先は、統合DB案v4の不足項目として補完する。

## 8. HEW展示戦略

90秒コース: 5号ケーキの色指定 → 飾り付け → メッセージ → 見積もり → 完成画像・製造指示書。

追加の展示導線: あらかじめ用意した公開作品を選択 → 自分用の構成へコピー → 色・飾りを変更 → 完成画像・製造指示書。体験開始のために会員登録を強制しない。デモ由来の構成を通常の公開ギャラリーや人気集計へ自動投入しない。

- デモモードはサーバー側設定のみで有効化し、URLパラメータで切り替えない。
- デモ注文はStripe・予約枠消費・個人情報入力をスキップし、`is_demo` を付与する。展示後にデモデータを削除する。
- 来場者単位の開始・終了・リセットが必要な場合のみ `demo_sessions` を使う。通常の会員セッションとは分離する。
- その場で番号付き俯瞰図と製造指示書をPDF出力するところまで見せる。
- PC1台とモニター2台を基本とし、モニター1は買い手画面、モニター2は店舗画面・製造指示書。
- デモ店舗は「CakeCanvas Demo Store」、住所「HEW展示会場」、電話番号 `000-0000-0000`。

持ち帰りは `designs` の構成データを保存し、推測困難なランダム共有IDのURLを表示・コピーできるようにする。PCブラウザで再描画して `canvas.toDataURL` で端末へ画像保存する。共有IDは内部IDと区別し、サーバーへ画像をアップロードしない。

モバイルルーターとローカル環境は2027年2月、回線断リハーサルまでに決定する。候補はノートPCの `next start` + ローカルPostgres + モバイルルーター。外部サービスを使わないデモ経路で動作確認する(通常のStripe・メール機能には外部接続が必要)。開場前のウォームアップ、予備環境起動、障害時の切替手順は構成決定後に確定する。

CG学科には3D操作・Blender、審査員には指示書生成・予約トランザクション・返金・マルチテナント設計を訴求する。ER図とアーキテクチャ図をパネルにする。
