# 企画書: CakeCanvas

作成日: 2026-07-17 / 最終改訂: 2026-09-12 / ステータス: 仕様決定・基礎学習開始前

2026-09-07の `plan/status.md` の決定を本文へ反映した。最新の決定・進捗は同ファイル、担当境界は `plan/technical-assignments.md` を参照する。資料間に差異があれば最新決定を優先して本文も更新する。新しい仕様・優先順位は4人全員の合意後に確定する。末尾の過去の決定履歴は当時の記録であり、現行仕様ではない。

## 1. 概要

CakeCanvasは、利用者が5号ケーキのスポンジ・クリームの色を指定し、3Dプレビュー上で飾りを自由に配置できるセミオーダーケーキサービスである。

注文情報から店舗向けの番号付き俯瞰配置図と製造指示書を生成し、予約枠、Stripeテスト決済、店頭受取までを扱う。ケーキ店へのSaaS提供を想定し、Ver1.0は1店舗・1注文1台の5号ケーキ・店頭受取のみとする。マルチテナントはDB設計のみ対応し、画面・デモは1店舗固定とする。

## 2. 背景・課題

- 電話・店頭・LINEでの曖昧な注文は、完成イメージの齟齬、聞き漏らし、価格の不透明さにつながる。
- 店舗は聞き取り・見積もり・仕様記録に時間を取られる。
- 買い手は自分でデザインした体験を求めるが、フルオーダーは高価で敷居が高い。

これらは現時点では仮説。旧企画で予定した9月中の実店舗1件へのヒアリングは、最新ステータスに完了記録がないため実施状況を週次確認する。聞き取り時間などの一次情報で裏付ける。

## 3. ターゲット

| 区分 | 対象 |
|---|---|
| 買い手 | 誕生日・記念日に贈る個人、主に10〜30代、推し活需要 |
| 顧客(課金対象) | オーダー対応の工数を減らしたい個人経営〜中規模のケーキ店 |

直接の顧客はケーキ店であり、買い手は店舗の顧客である。

## 4. 提供価値

- 買い手: 3Dで完成形を確認、自分で飾り付け、価格を即時確認、注文前に関連アレルゲンを確認できる。
- 店舗: 注文仕様が確定し、配置図つき製造指示書・予約枠・決済を一体で管理できる。
- 同じ配置データを3Dプレビューと製造指示書で共用することが中核となる。

## 5. 主要機能

### 買い手側

1. 5号固定のケーキでスポンジ・クリームの色を指定する。Ver0.5はプリセット3色、Ver1.0はカラーピッカー。色は `#RRGGBB` で保存する。
2. 外周デコを1つ選ぶ。既定は「なし」。選択肢と価格はコア機能完成後に確定するため、後から増やせるデータ設計にする。
3. フルーツ・チョコ・飾りを3D上でドラッグ配置し、回転・俯瞰で確認する。飾りは個数課金、初期上限12個。種類・上限は後から変更できる設計にする。
4. メッセージプレートは300円(税抜)、20文字、1行、書体1種類。改行・絵文字・機種依存文字は許可しない。
5. 注文確認画面で関連アレルゲン・店舗注記を表示し、確認時刻を保存する。
6. 日単位で受取日を選び、事前決済・即時キャプチャをStripeテストモードで行う。店頭受取番号を発行する。
7. ゲスト注文のみ。秘密トークン付きURLで照会・キャンセルする。
8. ステータスと日時から返金率を判定し、申請・返金結果・通知を記録する。
9. 展示では共有URLのQRから構成データを再描画し、完成画像を端末に保存できるようにする。

配送と手書きメッセージは実装しない。画像印刷は現行スコープ外で、2027-01-15に条件付きで採否を再判定する。買い手の会員登録は現行スコープ外だが廃止ではなく保留とし、4人の合意後に採否を決める。合意まではゲスト注文のみを実装する。

### 店舗側

1. パーツの登録・価格・アレルゲンを管理する。登録済みパーツは常に利用可能で、在庫数・提供可否フラグは持たない。
2. 製造ポイント制の日次キャパ、臨時休業、リードタイムを管理する。
3. 注文一覧・詳細・進捗更新を行う。不適切な注文を却下でき、店舗都合のキャンセルは100%返金する。
4. A4縦1枚の製造指示書を出力する。
5. 店舗スタッフのログインと管理画面のアクセス制御を行う。
6. Stripe返金失敗を確認し、店舗画面から再実行できるようにする。

### 5-A. アレルゲン

店舗が登録した原材料情報に基づく参考情報として提供し、最終確認は店舗が行う。実際に関係する品目を注文確認画面と製造指示書に表示する。

```text
allergens       (id, code, name, category, display_order)
part_allergens  (part_id, allergen_id, contains_type: contains | may_contain)
stores          (..., contamination_note)
```

選択パーツのアレルゲンを集計し、同一品目の `contains` と `may_contain` が競合する場合は `contains` を優先する。「含む」と「同一設備」を区別する。

除外フィルタ、追加前警告、28品目を分類する複雑なUIは実装しない。最終確認時刻は `orders.allergen_confirmed_at` に保存し、独立した同意履歴テーブルは作らない。

注意書き:
「表示内容は店舗が登録した原材料情報に基づく参考情報です。同一設備で卵・乳・小麦を含む製品を製造しています。重篤なアレルギーをお持ちの方は注文前に店舗へご相談ください。」

### 5-B. 注文・予約枠

5号1台を1製造ポイント、初期日次上限を5ポイントとする。受取枠は日単位で、時間帯別管理と飾り数のポイント加算は行わない。

```text
store_weekly_capacity (store_id, day_of_week, capacity_points)
daily_capacity       (store_id, date, capacity_points, reserved_points, is_closed, note)
stores.min_lead_days      -- 最短3日前まで受付
stores.max_advance_days   -- 受付上限日数(例:60日)
stores.order_cutoff_time  -- 締切時刻(例:17:00以降は翌日起算)
```

曜日別デフォルトを持ち、日付レコードは注文時にupsertする。繁忙期の上限上書きと臨時休業を設定できる。受取可能日の判定はAsia/Tokyoで行う。

- 決済開始時に枠を15分間仮確保する。予約枠の確認・更新はトランザクションと行ロックで保護し、過剰予約を防ぐ。
- 枠不足なら決済を開始しない。
- `payment_intent.succeeded` Webhookを根拠に注文確定する。仮確保分を確定時に二重消費しない。
- 期限切れは空き枠確認時にも解放し、Cronだけに依存しない。
- Stripeへの更新は注文IDを冪等性キーとして二重処理を防ぐ。
- 期限切れと決済成功が競合した場合の処理は、DB・決済設計時に①②で明文化する。

通常の状態遷移は `pending → confirmed → in_production → ready → completed`。例外は `cancelled`、`rejected`、`expired`。全遷移を `order_status_logs` に記録する。

店舗UIでは月カレンダーと残枠(例:残3/5pt)を表示し、日別キャパ・休業を編集する。満枠日は買い手側の日付選択を無効にする。

### 5-C. デザイン・製造指示書

```text
designs    (id, ..., locked_at)
placements (id, design_id, part_id, pos_x, pos_y, pos_z, rot_y, scale, seq_no)
orders     (id, design_id, ...)
```

- 注文前に `designs` を作り、配置は `placements.design_id` で保持する。JSON列ではなくテーブルに正規化する。
- `orders.design_id` が同じデザインを参照し、確定時に `designs.locked_at` を設定して編集を止める。
- 未注文デザインは7日、注文済みは受取日の30日後まで保持する。
- 注文確定時にパーツ名・単価・数量を `order_items` にコピーする。マスタ変更で過去の指示書や金額が変わらないようにする。
- 3DとSVGで同じ配置を読み、`(x, z)` を真上に投影したSVGを主図とする。`seq_no` を飾り明細と対応させる。
- 3D参考画像は印刷時にブラウザで生成し、サーバーに保存しない。失敗時もSVGだけで指示書を成立させる。

出力はA4縦1枚、ブラウザの印刷CSS(`@media print`)でPDF化する。記載順は以下とする。

1. 注文番号・受取番号・受取日・店舗名・印刷日時
2. 氏名・電話番号
3. 5号ケーキの仕様、外周デコ、スポンジ・クリームの色見本、実物との色差に関する注記
4. 番号付きの飾り明細(パーツ名・個数)
5. 番号付き俯瞰配置図、12時方向の基準線、直径mmのスケール
6. メッセージ原稿・書体・文字数
7. アレルゲン(含む/同一設備)・店舗注記
8. 備考
9. 製造完了・検品・引き渡しのチェック欄

SVGは白背景のベクタ図として印刷時の読みやすさを優先し、3D縮退時も共用する。

### 5-D. 認証・注文照会・個人情報

ゲスト照会URLは `/orders/{order_no}?t={token}`。トークンはランダム32バイト、DBにはSHA-256ハッシュを保存する。有効期限は受取日+30日。受取番号をWeb認証に使用しない。

- 受取番号: `MMDD-日別3桁連番` (例: `0907-023`)。店舗・受取日・連番の組み合わせを一意にする。
- 店頭照合: 下3桁と氏名または電話番号下4桁。
- 照会: トークン単位で15分30回。
- キャンセル: 確認画面を経由し、トークンとIP単位で15分5回。注文・返金の一意制約で二重実行を防ぐ。
- IPはハッシュ化し、制限超過時はHTTP 429。
- 氏名・電話番号・メールアドレスを必須とし、住所・フリガナは取得しない。
- 受取日の30日後に個人情報を匿名化する。金額・決済・返金履歴は個人情報から分離して保持する。

店舗スタッフは買い手と別の簡易セッション認証とし、Auth.jsは導入しない。`stores` にパスワードのbcryptハッシュを保持し、ログイン時に署名付きHttpOnly Cookieを発行する。管理画面の全ルートと各データ操作で認証・アクセス制御を行う。

## 6. 技術構成

| 領域 | 技術・方針 |
|---|---|
| アプリ | TypeScript、Next.js App Router |
| サーバーデータ | Server Components・Server Actionsを基本、Webhook等はRoute Handlers |
| UI・フォーム | Tailwind CSS、shadcn/ui、Zod、react-hook-form |
| 3D・状態管理 | React Three Fiber、drei、Zustand |
| モデル | Blender → 通常のGLB。合計2MBを超えた場合のみDracoを検討 |
| DB | Neon PostgreSQL + Prisma。マルチテナントを見据えてstore_idを保持 |
| 公開環境 | Vercel。PRごとのプレビュー |
| 決済・通知 | Stripeテストモード、Webhook、Resend |
| 製造指示書 | 自前SVG + ブラウザ印刷CSS |
| 日時 | date-fns・date-fns-tz。UTC保存、受取日はJSTの暦日、業務判定はAsia/Tokyo |
| 共通規約 | npm、Node.js LTS固定、内部IDはCUID、金額は整数円 |
| 品質確認 | TypeScript型チェック、ESLint、Vitest、Next.jsビルド |

Vercelは実行環境、Neonは永続データの保管先とする。Vercelのローカルファイルやプロセスメモリに業務状態を保持しない。画像はサーバーに保存しないため外部画像ストレージを導入しない。

- アプリ用はNeonのプーラ経由 `DATABASE_URL`、マイグレーション用は直結 `DIRECT_URL` とする。
- Prisma Migrateを使用し、マイグレーションファイルをGit管理する。
- Local・Vercel Preview・Productionを分け、Preview DBとProduction DBを共有しない。
- 秘密情報をGitHub・Discord・ソースコードへ保存しない。`.env` 系ファイルにCodexは触れない。
- プランの料金・制限・関数実行時間は環境構築時に公式情報で確認する。
- 展示開始前はウォームアップアクセスでNeon自動停止からの復帰を済ませる。

VercelはNext.jsとの適合性とPRプレビュー運用、Neonは自動停止からの自動復帰を理由に採用済み。ホスティングの再選定は行わない。

## 7. お金の流れ

### 価格計算(プロジェクト仕様)

```text
小計   = 5号ベース価格 + 外周デコ料金 + 飾り単価×個数 + メッセージプレート料金
消費税 = floor(小計 × 0.08)
合計   = 小計 + 消費税
```

色指定は0円。金額は整数円で保存し、税は小計に対して1回だけ計算・端数切り捨てとする。

| 項目 | 税抜仮価格 |
|---|---:|
| 5号ケーキ | 3,500円 |
| 色指定 | 0円 |
| メッセージプレート | 300円 |
| 苺 | 200円 |
| ラズベリー | 120円 |
| ブルーベリー | 80円 |
| チョコプレート | 150円 |
| 外周デコ | 未定(「なし」= 0円を既定とする) |

価格は初期実装用の仮値で、コア完成後に見直す。

### 履歴

| タイミング | 記録先 |
|---|---|
| 注文確定 | orders / order_items (価格スナップショット) |
| 決済成功Webhook | payments |
| キャンセル・返金 | refunds (返金率・理由・結果・失敗) |
| 注文ごとの手数料 | platform_fees |
| 店舗月額課金のモデル | store_subscriptions |

### 返金規定(ステータス×日時)

| 条件 | 返金率 |
|---|---:|
| 受取日の3日前まで、製造未着手 | 100% |
| 上記以外で前日23:59まで、製造未着手 | 50% |
| 製造中以降 | 0% |
| 当日・無連絡 | 0% |
| 店舗都合 | 時期を問わず100% |

50%返金は税込総額の50%を端数切り捨てで算出する。返金不可でも申請を残す。Stripe返金失敗は `failed` として記録し、店舗画面から再実行できるようにする。

SaaS収益モデルの月額5,000円は例示。プラットフォーム手数料は返金後に店舗へ残る金額の3%とする。店舗向け月次サマリ(売上・返金・手数料)は旧企画のVer1.5項目であり、着手時にコア完成状況と優先順位を確認する。実際の決済はStripeテストモードとする。

メールは注文受付・受取可・購入者キャンセル・店舗却下/返金の4種類。送信結果をDBへ記録し、同一メールを二重送信しない。

## 8. HEW展示戦略

90秒コース: 5号ケーキの色指定 → 飾り付け → メッセージ → 見積もり → 完成画像・製造指示書。

- デモモードはサーバー側設定のみで有効化し、URLパラメータで切り替えない。
- デモ注文はStripe・予約枠消費・個人情報入力をスキップし、`is_demo` を付与する。展示後にデモデータを削除する。
- その場で番号付き俯瞰図と製造指示書をPDF出力するところまで見せる。
- PC1台とモニター2台を基本とし、モニター1は買い手画面、モニター2は店舗画面・製造指示書。
- デモ店舗は「CakeCanvas Demo Store」、住所「HEW展示会場」、電話番号 `000-0000-0000`。

持ち帰りは `designs` の構成データを保存し、推測困難なランダム共有IDのURLをQR表示する。スマホで再描画して `canvas.toDataURL` で端末へ画像保存する。共有IDは内部IDと区別し、サーバーへ画像をアップロードしない。

モバイルルーターとローカル環境は2027年2月、回線断リハーサルまでに決定する。候補はノートPCの `next start` + ローカルPostgres + モバイルルーター。外部サービスを使わないデモ経路で動作確認する(通常のStripe・メール機能には外部接続が必要)。開場前のウォームアップ、予備環境起動、障害時の切替手順は構成決定後に確定する。

CG学科には3D操作・Blender、審査員には指示書生成・予約トランザクション・返金・マルチテナント設計を訴求する。ER図とアーキテクチャ図をパネルにする。

- main基準、ブランチは `feature/<Issue番号>-<説明>`。
- Conventional Commits、squash merge、PRレビュー1人以上。
