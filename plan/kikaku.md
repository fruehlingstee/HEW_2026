# 企画書:セミオーダーケーキ プラットフォーム(仮)

作成日:2026-07-17 / 最終改訂:2026-09-04 / ステータス:仮決定(9月改訂版)

## 1. 概要

サイズ・スポンジ・クリーム・フルーツなどを既定パーツから選び、**飾り付けはユーザー自身が3Dプレビュー上で自由に配置**できるセミオーダーケーキ注文サービス。

注文データから店舗向けの**製造指示書(飾り配置図つき)を自動生成**し、予約枠・決済・店頭受け渡しまでを一気通貫で扱う。ケーキ店に導入してもらう**SaaS(プラットフォーム提供型)** として設計し、HEWでは架空の1店舗でデモする。

## 2. 背景・課題

- オーダーケーキは現状、電話・店頭・LINEでの曖昧なやり取り(「こんな感じで」と画像を送る)が主流。完成イメージの齟齬、聞き漏らし、価格の不透明さがトラブルの元
- 店側は注文の聞き取り・見積もり・仕様の記録に時間を取られ、小規模店ほど負担が大きい
- 買い手は「自分でデザインした」体験を求めるが、フルオーダーは高価で敷居が高い

**→ セミオーダー(既定パーツ)+ユーザー配置(自由な飾り付け)の中間形で、双方の課題を解決する。**

> ※ 上記は現時点で仮説。9月中に実店舗1件へのヒアリングを行い、一次情報(1件あたりの聞き取り所要時間など)で裏付ける(保留論点を参照)。

## 3. ターゲット

| 区分 | 対象 |
|---|---|
| 買い手(エンドユーザー) | 誕生日・記念日にケーキを贈る個人(メイン:10〜30代)、推し活のオタクケーキ需要 |
| **顧客(課金対象)** | **個人経営〜中規模のケーキ店**(オーダー対応の工数を減らしたい店) |

**本サービスの直接の顧客はケーキ店であり、買い手は店舗の顧客である**(SaaSモデル)。収益構造は第7章を参照。

## 4. 提供価値

- **買い手**:完成形を3Dで確認してから注文できる/「自分で飾り付けた」体験/価格がリアルタイムに見える/アレルゲンが自動表示される
- **店舗**:聞き取り工数を大幅削減し仕様が確定/配置図つき製造指示書が自動で出る/予約枠と決済の管理が一体化

## 5. 主要機能

### 買い手側

1. **ベース選択(セミオーダー)**:サイズ→スポンジ→クリーム→外周デコをステップ形式で選択。選ぶたびに価格が即時更新
2. **飾り付けエディタ(ユーザー製作)**:3Dケーキにフルーツ・チョコ・飾りをドラッグ&ドロップで自由配置。回転・俯瞰で確認。**飾りは個数課金・サイズ別の配置上限あり**(価格・指示書・見た目の破綻防止)
3. **メッセージプレート**:手書き入力(Canvas)または書体選択。**プリントできるのはメッセージのみ**(写真・イラスト等の画像プリントは提供しない)
4. **アレルゲン自動表示**:選択パーツから自動集計(詳細は 5-A)
5. **受け取り**:**店頭受取のみ**。受取番号を発行し店頭で照合(配送は提供しない)
6. **決済**:事前決済・即時キャプチャ(Stripeテストモード)。注文確認・進捗通知(受付→製造中→受取可)は**メール+アプリ内照会画面**で通知
7. **キャンセル・返金**:**ステータス×日時の2軸**で返金率を自動判定し**完全自動**(申請→返金率自動判定→Stripe即時返金→`refunds`テーブルに記録→確認メール)。規定は第7章
8. **認証・注文照会**:ゲスト注文は**ワンタイムトークン付きURL**で照会・キャンセル。段階実装:Ver0.5はゲストのみ→Ver1.0で会員機能(詳細は 5-D)
9. **完成画像の持ち帰り**:完成ケーキ画像を書き出し、**QRコード経由で来場者のスマホに保存**(HEW展示のSNS導線。第8章)

### 店舗側

1. **パーツCMS**:パーツ(スポンジ・フルーツ・飾り)の登録・価格・アレルゲン・提供可否フラグの管理。**在庫数は持たない**(パーツは都度仕入れ前提、ボトルネックは製造キャパ)
2. **予約枠管理**:**製造ポイント制**の日次キャパ管理+リードタイム設定(詳細は 5-B)
3. **注文管理**:注文一覧、ステータス更新(受付→製造中→受取可→完了)。不適切なメッセージ内容を店舗が却下できるフロー(却下時は100%返金)
4. **製造指示書の自動生成**:構成一覧+番号付き飾り配置図+メッセージプレート原稿+アレルゲン欄(詳細は 5-C)

### 5-A. アレルゲン自動表示(詳細)

#### 法的な位置づけ

対面販売の生菓子は食品表示法上の**容器包装表示義務の対象外**だが、アレルギー情報の提供は事故防止上の実務標準である。本サービスは**「参考情報の提供」**として位置づけ、最終確認は店舗が行う建て付けとする。

#### 対象品目

| 区分 | 品目数 | ケーキで実際に該当するもの |
|---|---|---|
| **特定原材料**(表示義務) | 8品目 | **卵・乳・小麦**(ほぼ全構成)、**くるみ**、えび・かに・そば・落花生 |
| **特定原材料に準ずるもの**(表示推奨) | 20品目 | **アーモンド・カシューナッツ**(ナッツ飾り)、**オレンジ・キウイ・バナナ・もも・りんご**(フルーツ)、**大豆**(レシチン)、**ゼラチン**(ムース・ナパージュ)、ごま |

※ くるみは義務品目に移行済み(8品目化)。ナッツ飾りを扱うため正確に保持する。

#### データモデル

```
allergens       (id, code, name, category: mandatory | recommended, display_order)
part_allergens  (part_id, allergen_id, contains_type: 'contains' | 'may_contain')
stores          (..., contamination_note)
```

**設計の肝は `contains_type`。**「含む」と「同一設備で製造(may_contain)」を型として分離して保持する。単純集計との差別化点であり、発表での説明ポイントとなる。

#### 集計ロジック

1. 選択パーツ集合のアレルゲンを UNION
2. 同一アレルゲンで `contains` と `may_contain` が競合した場合は `contains` を優先
3. 義務8品目は常時表示、推奨20品目は開閉式で表示

#### UI仕様

- **エディタ上部に常時アレルゲンバッジ**:飾りを配置するたびリアルタイム更新
- **追加前プレビュー**:「このパーツを追加すると『くるみ』が加わります」
- **除外フィルタ**:「卵不使用で絞り込む」→ 該当パーツをグレーアウト
- 注文確認画面での**最終確認チェックボックス**(同意ログをDBに記録)

#### 免責表示(必須)

- 「表示は店舗登録データに基づく参考情報です」
- **コンタミネーション注記**:「同一設備で小麦・卵・乳を含む製品を製造しています」(店舗ごとに設定)
- 「重篤なアレルギーをお持ちの方は店舗へ直接ご相談ください」

製造指示書にもアレルゲン欄を設け、店舗が厨房で最終確認できるようにする。

### 5-B. 予約枠管理(詳細)

#### 製造ポイント制

サイズにより製造工数が異なるため、単純な個数上限ではなく**製造コスト(ポイント)**で管理する。

| サイズ | 製造ポイント(例) |
|---|---|
| 4号 | 1.0 |
| 5号 | 1.5 |
| 6号 | 2.0 |
| 7号 | 3.0 |

```
store_weekly_capacity (store_id, day_of_week, capacity_points)          -- 曜日別デフォルト
daily_capacity        (store_id, date, capacity_points, reserved_points,
                       is_closed, note)                                  -- 日付単位の実績・例外
```

- 曜日別デフォルトを持ち、**日付レコードは注文時に upsert**(事前の一括生成は不要)
- **繁忙期の手動上書き**:クリスマス・バレンタインは capacity を絞る(ケーキ店の実務を反映)
- 飾り個数のポイント加算は**将来拡張**とし、初期はサイズのみで算出する

#### リードタイム

```
stores.min_lead_days      -- 例:3日前まで受付
stores.max_advance_days   -- 例:60日先まで受付
stores.order_cutoff_time  -- 例:17:00以降の注文は翌日起算
```

#### 同時注文の競合対策

- 決済確定処理をトランザクションで囲み、`daily_capacity` 行を **`SELECT ... FOR UPDATE`** でロックして `reserved_points` を加算
- 枠不足なら決済を実行せずロールバック
- カートでの仮押さえは複雑なため Ver1.0 では非対応とし、決済直前に最終判定する

**この予約枠のトランザクション設計は、RDB必須要件に対する主要なアピールポイントとする**(発表パネルに掲載)。

#### 店舗UI

- 月カレンダー表示、各日に「残 3.5 / 8.0 pt」のバー
- 日クリックで capacity 編集・臨時休業トグル
- 満枠日は買い手側の日付選択でグレーアウト

### 5-C. 製造指示書(詳細)

#### 出力形式

**A4縦1枚 / ブラウザの印刷CSS(`@media print`)でPDF化。** 追加ライブラリ不要で確実に動作する。厨房で紙として使うため、1枚に収めることを最優先とする。

#### 記載項目(レイアウト順)

1. **ヘッダ**:注文番号 / 受取番号 / 受取日 / 店舗名 / 印刷日時
2. **お客様情報**:氏名・電話番号(店頭照合用)
3. **ケーキ仕様**:サイズ(号数)/ スポンジ / クリーム / 外周デコ
4. **飾り明細**:パーツ名 × 個数の集計表(①②③…の番号付き)
5. **配置図**:俯瞰図。飾りに項目4の番号を対応表示。**12時方向を基準線として明示**(向きの取り違え防止)+ 直径mmのスケール
6. **メッセージプレート**:原稿テキスト+書体名、または手書き画像を原寸で
7. **アレルゲン欄**:含む / 同一設備(店舗の最終確認用)
8. **備考**
9. **作業チェック欄**:製造完了 □ / 検品 □ / 引き渡し □

#### 配置図のレンダリング方式(決定)

| 観点 | A案:3D真上カメラのスクショ | B案:配置座標から2D SVG描画 |
|---|---|---|
| 実装工数 | 最小 | 小〜中 |
| 印刷適性 | ✕ 影と色で潰れる | ◎ 白背景の線画 |
| **番号の付与** | **✕ 不可** | **◎ 可能** |
| 3D縮退時 | 消滅 | 生き残る |
| 拡大耐性 | ラスタ | ベクタ |

**決定:B案を主図とし、A案(3Dスクショ)を参考画像として小さく併載する。**

番号を振って飾り明細と対応させられることが厨房での実用性を決めるため。実装は配置座標の `(x, z)` を真上に投影し、SVGで円+ラベルを描画するのみで軽い。「見た目の確認(A)」と「作業指示(B)」を両立できる。

#### データ設計

```
placements (id, order_id, part_id, pos_x, pos_y, pos_z, rot_y, scale, seq_no)
```

- **JSON列ではなくテーブルに正規化する**(RDB必須要件へのアピールとして有利)
- `seq_no` が指示書の①②③番号に対応する
- **3Dプレビューと製造指示書が同一テーブルを読む**ことで、「1つのデータから2つのアウトプット」という本企画の核心を実装レベルで裏付ける

#### スナップショット

注文確定時にパーツ名・価格を `order_items` にコピーして固定する。後からパーツマスタの価格や名称が変わっても、過去の指示書と金額履歴が変化しない(履歴の一貫性)。

### 5-D. 認証・注文照会(詳細)

#### ゲスト注文の照会・キャンセル

- 注文完了メールに**ワンタイムトークン付きURL**を記載:`/orders/{order_no}?t={token}`
- トークンは**ランダム32バイト、DBにはハッシュで保存**
- 有効期限:**受取日 + 30日**
- 用途:注文照会 / 進捗確認 / キャンセル申請
- **レート制限**を設ける(トークン漏洩時のキャンセル悪用対策)

#### 受取番号との使い分け

| | 用途 | 形式 |
|---|---|---|
| **受取番号** | 店頭での引き渡し照合 | 6桁の短い番号(口頭で伝達可能) |
| **照会トークン** | Web上の注文照会・キャンセル | 32バイトのランダム値 |

**両者は別物として設計する。** 受取番号を推測されてもWeb上では何も操作できない。

#### 段階実装

- Ver0.5:ゲストのみ(トークン照会)
- Ver1.0:会員登録(Auth.js)。ゲスト注文を後から会員アカウントに紐付け可能とする

## 6. 技術構成

| 領域 | 技術 | 難易度 | 見せ場・役割 |
|---|---|---|---|
| フレームワーク | **Next.js(App Router)/ TypeScript** ※要チーム承認 | ★★☆☆☆ | フロント・API統一。Vercel公開と相性最良 |
| 3Dプレビュー | React Three Fiber + drei | ★★★★★ | レイキャストによる表面へのドラッグ配置 |
| 3Dモデル | Blender → glTF(Draco圧縮) | ★★★★☆ | ローポリでモバイル対応 |
| 状態管理 | Zustand | ★★☆☆☆ | 3Dエディタの配置状態管理 |
| DB | PostgreSQL(Neon / Supabase)+ Prisma | ★★★☆☆ | 注文・決済・返金の全履歴、配置座標。全テーブルに `store_id` |
| 認証 | Auth.js(NextAuth)+ 自前トークン照会 | ★★★☆☆ | ゲスト+会員の両対応 |
| 決済 | Stripe(テストモード)+ **Webhook** | ★★★★☆ | 決済・返金のトランザクション。`payment_intent.succeeded` で注文確定 |
| メール | Resend | ★☆☆☆☆ | 注文確認・進捗・キャンセル通知 |
| 画像保存 | Vercel Blob(署名付きURL) | ★★☆☆☆ | **手書きプレートPNGのみ**(画像プリント廃止により縮小) |
| **指示書PDF** | **印刷CSS(`@media print`)** | ★★☆☆☆ | A4縦1枚。追加ライブラリ不要 |
| **俯瞰配置図** | **SVG(自前描画)** | ★★★☆☆ | 番号付き作業図。3D縮退時も生存 |

**マルチテナントはDB設計のみ対応**(全テーブルに `store_id`。画面・デモは1店舗固定、発表資料で説明)。

**配置座標データは `placements` テーブルに保存し、プレビューと製造指示書の両方で共用する**(1つのデータから2つのアウトプット)。

## 7. お金の流れ(IH専攻規定への適合)

### 価格計算

```
小計   = ベース価格(サイズ・スポンジ・クリーム・外周デコ)
       + 飾り価格(個数課金)
       + メッセージプレート料金
消費税 = 小計 × 8%(軽減税率・持ち帰り)  ※合計に対して1回、端数切り捨て
合計   = 小計 + 消費税
```

- **店頭受取のみのため税率は8%単一**(配送料10%との混在が発生しない)
- 金額はすべて**整数(円)**でDBに保存。丸めルールを明記する

### トランザクション記録

| タイミング | 記録先 |
|---|---|
| 注文確定 | `orders` / `order_items`(価格スナップショット) |
| 決済成功(Stripe Webhook) | `payments` |
| キャンセル・返金 | `refunds`(返金率・理由・自動判定結果) |
| 注文ごとの手数料 | `platform_fees` |
| 店舗の月額課金 | `store_subscriptions` |

**注文1件ごとにプラットフォーム手数料レコードを生成する**ことで、金銭の流れをデータで完全に追跡できる。

### 返金規定(ステータス×日時の2軸)

| 条件 | 返金率 |
|---|---|
| 受取日の**3日前まで**(製造未着手) | 100% |
| **前日23:59まで**(製造未着手) | 50% |
| ステータス = **製造中** 以降 | 0% |
| 当日・無連絡 | 0% |
| **店舗都合**のキャンセル | 100%(時期を問わず) |

「製造未着手」を条件に含める点が要点で、リードタイム3日とも整合する。

### SaaS収益モデル(数値は例示)

- 店舗月額:**5,000円 / 月**
- プラットフォーム手数料:**注文額の 3%**
- 別途 Stripe決済手数料 3.6% が発生する旨も明示する
- 店舗向け**月次サマリ画面**(売上・返金・手数料)を Ver1.5 で提供

**全ての金銭のやり取りをデータとして残す(規定準拠)。実際の決済はStripeテストモードで想定。**

## 8. HEW展示戦略

### 90秒体験コース

サイズ選択 → クリーム → **飾り付け(メイン)** → メッセージ → 見積もり表示 → 完成画像

画像プリントと配送設定を廃止したことで、飾り付けに集中した導線となった。

### 最大の見せ場:その場で製造指示書が出る

デモモードでは決済をスキップし、**来場者が飾ったケーキの製造指示書がその場でPDF出力される**ところまで見せる。「裏側まで動いている」ことが一目で伝わり、「ただのEC」評価への反証となる。

### 持ち帰り導線

- 完成ケーキ画像を書き出し(`canvas.toDataURL`)
- **QRコードを画面表示 → 来場者が自分のスマホで読み取って保存**(SNS導線)

### 会場ネットワーク対策

「Vercel公開で来場者のスマホから操作」は会場Wi-Fi断で全滅するため、二重化する。

- 本番:Vercel
- **フォールバック:ノートPC上でローカル実行(`next start` + ローカルPostgres)+ モバイルルータ**
- 事前に**回線断リハーサル**を実施

### 学科別の訴求

- **ゲーム・CG学科**:Three.jsの3D操作+Blenderモデリング
- **IH専攻・審査員**:製造指示書の自動生成、予約枠のトランザクション設計、返金処理、マルチテナント設計
- 掲示物として**ER図とアーキテクチャ図をパネル化**する

### 実機

タブレット2〜3台 + 来場者スマホ(学校の機材確保状況を確認のうえ決定)

## 決定事項

### 2026-07-17

- **価格計算**:飾りパーツは個数課金+サイズ別の配置上限あり
- **在庫管理**:予約枠(製造キャパ)のみ管理。パーツは提供可否フラグのみ、在庫数は持たない
- **マルチテナント**:DB設計のみ対応(`store_id`)。画面・デモは1店舗固定
- **認証**:ゲスト注文+会員登録の両対応(Ver0.5はゲストのみ→Ver1.0で会員機能)
- **進捗通知**:メール+アプリ内照会画面
- **公開・デモ方式**:Vercelで公開し、来場者のスマホからも操作可能にする

### 2026-09-04(改訂)

- **画像プリント機能:不採用。** プリント対象はメッセージプレートのみ
- **受け取り:店頭受取のみ。** 配送・配送料はスコープ外(郵便番号ゾーン制の決定は破棄)
- **決済:事前決済・即時キャプチャ**(画像承認フロー廃止によりオーソリ分離は不要)
- **消費税:軽減税率8%の単一税率**(店頭受取=持ち帰り)
- **認証:ゲストはワンタイムトークン付きURLで照会・キャンセル。** 受取番号とは別物として設計
- **返金:ステータス×日時の2軸判定**(製造着手後は0%)
- **予約枠:製造ポイント制+リードタイム**(最短3日・締切時刻・受付上限日数)
- **配置図:B案(2D SVG・番号付き)を主図、3Dスクショを参考併載**(保留論点を解消)
- **製造指示書:A4縦1枚・印刷CSSでPDF化**
- **配置座標:JSON列ではなく `placements` テーブルに正規化**
- **Ver0.5:10月末に再設定**(8月末から2ヶ月延期)
- **機能凍結:1月末**
- ▲ **バックエンド:Next.js フルスタックを提案 — チーム承認待ち**
