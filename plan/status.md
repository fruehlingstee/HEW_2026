# CakeCanvas プロジェクトステータス

最終更新: 2026-09-07  
ステータス: 仕様決定・基礎学習開始前

## 概要

CakeCanvasは、5号ケーキのスポンジ色・クリーム色を指定し、飾りを3Dプレビュー上で自由に配置できるセミオーダーケーキサービスである。注文情報から店舗向けの俯瞰配置図と製造指示書を生成し、予約枠、テスト決済、店頭受取までを扱う。

Ver1.0は1店舗・1注文1ケーキ・店頭受取のみ。登録済みパーツは常に注文可能とし、在庫数と提供可否は管理しない。

## 技術・開発方針

- 正式名称はCakeCanvas。リポジトリ名は`HEW_2026`を維持する。
- TypeScript、Next.js App Router、Tailwind CSS、shadcn/ui、Zod、react-hook-form、Vitestを採用する。
- npmとNode.js LTSを使用する。
- Server ComponentsとServer Actionsを基本とし、サーバー状態管理ライブラリは初期導入しない。
- 日時はUTCで保存し、受取日と業務判定はAsia/Tokyoで扱う。date-fnsとdate-fns-tzを共通処理に使う。
- 内部IDはCUID、金額は円単位の整数とする。
- Prisma Migrateを使い、マイグレーションファイルをGitで管理する。
- Local、Vercel Preview、Productionを分け、Preview DBとProduction DBを共有しない。
- 秘密情報をGitHub、Discord、ソースコードへ保存しない。`.env`系ファイルはCodexの編集対象外とする。
- CIで型チェック、ESLint、Vitest、Next.jsビルドを実行する。
- APIエラー形式を統一し、決済、Webhook、返金結果はDBへ記録する。

## Git・Issue運用

- `main`を基準とし、ブランチは`feature/<Issue番号>-<説明>`とする。
- Conventional Commits、squash merge、1人以上のPRレビューを必須とする。
- GitHub Projectsは`Backlog → Ready → In Progress → Review → Done`で管理する。
- #24を親Issue、#4〜#23を直接の子Issueとして登録する。作業順序はblocked-by関係で表す。
- 毎週金曜日に30分の進捗確認を行い、本ファイルへ進捗、次の作業、ブロッカーを記録する。
- 作業時間は管理せず、各担当が完成時に報告する。ただし技術的に詰まった場合は完成前に共有する。

## 商品・画面仕様

- 1注文は5号ケーキ1台。外周デコは提供しない。
- スポンジ色とクリーム色は利用者が自由指定できる設計とする。Ver0.5はプリセット3色、Ver1.0はカラーピッカーを使う。
- 色は`#RRGGBB`で保存し、製造指示書に色見本と実物との差異に関する注記を載せる。
- 登録済みパーツは常に利用可能とし、在庫数・提供可否を持たない。
- 初期PoCは5号土台と苺。成功後にラズベリー、ブルーベリー、チョコプレートを追加する。
- 飾りの初期上限は12個だが、種類と上限は変更可能なデータ設計にする。
- メッセージプレートは300円、20文字、1行、書体1種類。改行、絵文字、機種依存文字は禁止する。

## デザイン・3D

- `designs`を注文前に作り、`placements.design_id`で配置を保持する。
- `orders.design_id`で注文と結び、注文確定時に`designs.locked_at`を設定する。
- 共有IDは推測困難なランダム値。未注文デザインは7日、注文済みデザインは受取日の30日後まで保持する。
- 3D参考画像はサーバーへ保存せず印刷時に生成する。失敗時も俯瞰SVGだけで指示書を成立させる。
- 通常のGLBから始め、合計2MBを超えた場合だけDraco圧縮を検討する。
- 性能目標は初期表示3秒以内、操作中30fps以上、土台500KB以下、飾り1種類150KB以下。
- 3D縮退時はSVG上の真上視点ドラッグ配置と簡易側面図の2.5D画面へ移行する。

## 注文・予約・決済

- 5号ケーキ1台を1製造ポイントとし、初期の日次上限は5ポイント。
- 受取枠は日単位。飾り数は製造ポイントへ加算しない。
- 決済開始時に15分間仮確保し、Stripeの`payment_intent.succeeded` Webhookで注文を確定する。
- 期限切れ仮確保は空き枠確認時にも解放し、Cronだけに依存しない。
- Stripeへの更新は注文IDを冪等性キーとして二重処理を防ぐ。

### 注文ステータス

`pending → confirmed → in_production → ready → completed`

例外状態は`cancelled`、`rejected`、`expired`。全遷移を`order_status_logs`へ記録する。

### 受取番号・照会

- 受取番号は`MMDD-日別3桁連番`（例: `0907-023`）。店舗・受取日・連番を一意にする。
- 店頭では下3桁と氏名または電話番号下4桁で照合する。受取番号はWeb認証に使わない。
- 32バイトの秘密トークンを発行し、DBにはSHA-256ハッシュを保存する。
- 注文照会はトークン単位で15分30回、キャンセルはトークンとIP単位で15分5回まで。
- IPはハッシュ化し、超過時はHTTP 429を返す。キャンセルと返金は一意制約とStripe冪等性キーで二重実行を防ぐ。

## 個人情報・アレルゲン

- 氏名、電話番号、メールアドレスを必須とし、住所とフリガナは取得しない。
- 受取日の30日後に個人情報を匿名化し、金額と決済・返金履歴は分離して保持する。
- アレルゲン除外フィルタ、追加前警告、28品目の複雑なUIは実装しない。
- 注文確認画面と製造指示書に、実際に関係するアレルゲンと店舗注記を表示する。
- `orders.allergen_confirmed_at`を保存し、独立した同意履歴テーブルは作らない。
- 注意書き: 「表示内容は店舗が登録した原材料情報に基づく参考情報です。同一設備で卵・乳・小麦を含む製品を製造しています。重篤なアレルギーをお持ちの方は注文前に店舗へご相談ください。」

## 返金・通知

- 50%返金は税込総額の50%を端数切り捨てで算出する。返金不可でも申請記録を残す。
- Stripe返金失敗は`failed`として記録し、店舗画面から再実行可能にする。
- プラットフォーム手数料は返金後に店舗へ残る金額の3%。
- メールは注文受付、受取可、購入者キャンセル、店舗却下・返金の4種類。
- 送信結果をDBへ記録し、同じメールの二重送信を防ぐ。

## デモ・展示

- デモモードはサーバー側設定でのみ有効化する。
- デモ注文はStripe、予約枠消費、個人情報入力をスキップし、`is_demo`を付ける。
- 展示終了後にデモデータを削除する。
- PC1台とモニター2台を基本とし、買い手画面と店舗画面・指示書を分けて表示する。
- デモ店舗は「CakeCanvas Demo Store」、住所は「HEW展示会場」、電話番号は`000-0000-0000`。
