## 目的

4人が機能を縦に担当しつつ、結合時の責務漏れを防ぐための技術分担表である。
本書は実装担当と技術的な境界を扱う。2026-09-07の決定を反映済み。差異がある場合は `plan/status.md` の最新決定を優先し、関連本文も更新する。新しい仕様変更は4人全員の合意後に確定する。

## 全体方針

- 共通言語は **TypeScript** とする。フロントエンド、API、DBアクセスでデータ型を揃える。
- フレームワークは **Next.js（App Router）** とし、画面とAPIを同一リポジトリで実装する。
- DBは **Neon PostgreSQL + Prisma**、公開環境は **Vercel** とする。
- 3Dは **React Three Fiber + drei**、モデル作成は **Blender → glTF（Draco圧縮）** とする。
- 編集用配置は `placements` へ正規化し、公開時・注文時は構成スナップショットを固定保存する。編集・公開・製造指示書で座標契約を共通化する。
- 買い手は会員・ゲスト注文に対応する。会員登録、マイページ、公開ギャラリー、お気に入り、人気順、公開作品のコピーを追加予定とする。配送、手書きメッセージ、SNSログインは対象外。画像印刷は従来の再判定条件による。

## 技術の重さ

| 技術 | 重さ | 主な難所 |
|---|---|---|
| TypeScript | 低〜中 | 共通型を保ち、`any` に逃げないこと |
| Next.js App Router | 中 | Server / Client Componentの分離、画面とAPIの接続 |
| Neon PostgreSQL + Prisma | 中〜高 | 正規化、注文履歴の固定、接続プーラ |
| Stripe + Webhook | 高 | 決済成功時の確定、返金、二重処理の防止 |
| React Three Fiber + drei | 非常に高 | レイキャスト、ドラッグ配置、PCでの操作・描画性能 |
| Blender → glTF | 高 | モデル軽量化、Web用座標系、見た目と性能の両立 |
| Zustand | 中 | 3D配置・選択内容・価格表示の状態同期 |
| SVG自前描画 | 中〜高 | 3D座標を番号付き俯瞰図に変換すること |
| 印刷CSS | 低〜中 | A4縦1枚の製造指示書レイアウト |
| Resend | 低 | 通知の送信契機と内容 |
| Vercel | 低〜中 | Neon接続、環境設定、PRプレビュー運用 |

## ① バックエンド・進行管理

### 担当技術

TypeScript / Next.js Server Components・Server Actions・Route Handlers / PostgreSQL / Neon / Prisma / Stripe / Resend / Vercel / GitHub Projects

### 担当範囲

- 進行管理、タスク分解、週次進捗確認、PRレビュー運用
- DBの基本設計とマイグレーション管理
- 共通のドメイン型（注文、パーツ、価格、配置、アレルゲン）の定義
- 買い手向け注文API、注文照会API、キャンセルAPI
- Stripe Payment Intentの作成、Webhook検証、決済成功後の注文確定
- 返金率の自動判定、Stripe返金、`refunds` への記録
- 注文受付、受取可、購入者キャンセル、店舗却下・返金に加え、会員のメール確認・パスワード再設定通知と、送信結果・二重送信防止のDB管理
- 追加案: 会員・認証・店舗所属の共通データ、本人と店舗の権限確認、公開・お気に入り・コピーのAPIを④・②と接続する
- Vercel + Neonの接続、PRプレビュー、CIの土台

### 必ず満たす実装条件

- 注文確定は画面遷移ではなく、`payment_intent.succeeded` Webhookを根拠に行う。
- 決済対象を作る時点でパーツ名・単価・数量を `order_items`、構成・配置・アレルゲンを `order_design_snapshots` に固定保存する。元デザインやマスタを後から変更しても既存注文へ反映しない。
- Neonは接続プーラ経由の `DATABASE_URL` をアプリ用、直結の `DIRECT_URL` をマイグレーション用として使う。
- DB設計と決済確定処理は②がレビューし、①のみが把握する状態を作らない。
- 編集デザインは `placements.design_id`、注文の元デザインは `orders.source_design_id` で参照する。元デザインを一律ロックせず、注文時スナップショットの不変性を保証する。
- 決済開始時に予約枠を15分間仮確保し、空き枠確認時にも期限切れを解放する。Stripe更新の冪等性と、全状態遷移の `order_status_logs` 記録を保証する。

### 重さとリスク

StripeとDBトランザクションが高難度である。決済、予約枠の消費、注文確定、メール送信の順序を誤ると二重注文・過剰予約・通知漏れが起きる。

## ② バックエンド兼店舗側フロント

### 担当技術

TypeScript / Next.js / PostgreSQL / Neon / Prisma / 印刷CSS / 自前セッション認証

### 担当範囲

- パーツCMS（価格、アレルゲン、新規利用の有効／無効）の店舗画面。在庫数は管理しない
- 注文一覧、注文詳細、受付→製造中→受取可→完了の状態更新画面
- 製造ポイント制の予約枠、日別キャパ、臨時休業の管理画面
- 共通会員認証に接続した店舗スタッフ用ログインと、店舗所属・roleによる管理画面・各操作のアクセス制御
- A4縦1枚の製造指示書を印刷CSSで作成
- 飾り明細、メッセージ原稿、アレルゲン、チェック欄を指示書へ配置
- ④が作る番号付き俯瞰SVGを製造指示書へ組み込む

### 必ず満たす実装条件

- 予約枠は日単位、5号1台を1ポイント、初期日次上限を5ポイントとする。時間帯別管理・飾り数の加算は行わない。
- 仮確保・期限切れ解放・確定時のキャパ処理は①と連携する。決済開始前に枠不足を検出し、二重消費・過剰予約を防ぐ。
- 指示書は厨房作業用とし、3Dの見栄えより白背景で読めることを優先する。
- 店舗スタッフも共通の `users`・`auth_sessions` で本人を確認し、`store_memberships` で店舗単位の権限を検証する。店舗共通パスワードを使わない。

### 重さとリスク

画面数は多いが、3D・決済より不確実性は低い。予約枠と製造指示書は業務価値の中心であり、①のDB設計レビューを通じて結合する。

## ③ 3D・Blender

### 担当技術

TypeScript / React Three Fiber / drei / Three.js / Blender / glTF / Draco圧縮 / Zustand

### 担当範囲

- 5号土台と苺でPoCを作り、成功後にラズベリー、ブルーベリー、チョコプレートを追加する。
- UIデザイン、Blenderから通常のGLBへの書き出し、Webでの表示検証。Dracoは合計2MB超過時のみ検討する。
- R3Fの3Dシーン、カメラ、ライト、回転・俯瞰表示
- レイキャストによるケーキ表面へのドラッグ配置
- 配置ごとの `pos_x`、`pos_y`、`pos_z`、`rot_y`、`scale` の作成・更新
- 保存した配置座標から3D配置を再現する処理
- 追加案: 公開版・コピー元・注文スナップショットから同じ構成を再現し、現在の資産との互換性を④と確認する
- ④と共同で配置データの形式を確定する

### 必ず満たす実装条件

- PCブラウザでglTFケーキモデルを表示する。
- 飾りをドラッグして配置し、座標をDBへ保存する。
- 保存座標から同じ配置を再表示する。
- モデルは精密さより軽量さとパーツの見分けやすさを優先する。
- 目標は初期表示3秒以内、操作中30fps以上、土台500KB以下、飾り1種類150KB以下とする。

### 重さとリスク

本プロジェクトで最も難しい領域。レイキャスト、モデル座標、ドラッグ中の表示、描画性能を同時に扱う必要がある。
2026-10-30にPCで上記3条件を検証する。未達ならSVG上の真上視点ドラッグ配置と簡易側面図による2.5Dへ縮退する。

## ④ 3D兼買い手側フロント

### 担当技術

TypeScript / Next.js / React / React Three Fiber / drei / Zustand / SVG自前描画 / CSS方針としてTailwind CSS + shadcn/ui（採用決定後）

### 担当範囲

- 5号・6号を選び、スポンジ・クリームの色を指定するステップUI。Ver0.5はプリセット3色、Ver1.0はカラーピッカー
- 飾り付けエディタと買い手画面の接続
- 追加案: 会員登録・ログイン・プロフィール・マイページ、公開ギャラリー・人気順・お気に入り・コピー開始画面を①のAPIと接続する
- リアルタイム価格、種類別の飾り上限（フルーツ・スイーツ・ミント20個、絞りクリーム32個、お祝いの飾り10個）、注文確認画面の関連アレルゲン・店舗注記・確認チェック。除外フィルタと追加前警告は実装しない。
- 注文確認前の構成確認画面
- 注文受付後の購入者向け画面をPC・スマホ対応にする（受付完了、照会、キャンセル申請、返金状況確認）。①と共通API・トークン認証を接続し、iPhone Safari／Android Chromeでタップ操作を確認する。
- 配置データの `(x, z)` を真上から投影する番号付き俯瞰SVG
- SVGと飾り明細の `seq_no` を対応させる処理
- 3D縮退時の2.5D買い手画面への切り替え
- HEW展示向けの90秒体験コースと完成画像持ち帰り導線の画面

### 必ず満たす実装条件

- 買い手は、5号ケーキの色指定→飾り付け→メッセージ→見積確認までを短時間で完了できる。
- 俯瞰SVGは3Dのスクリーンショットではなく、配置座標からベクタとして描画する。
- SVGの番号と、製造指示書の飾り明細の番号を一致させる。
- 編集時の `placements` と公開・注文時スナップショットで座標契約を共通化し、描画方法ごとに別の座標形式を持たない。

### 重さとリスク

3Dと通常のUIの接続が難所である。俯瞰SVGは3D縮退後も製造指示書に残るため、早期に作って無駄にならない構成にする。

## 共通データの最低要件

`placements` は編集用の配置データである。公開版・注文スナップショットも同じ座標契約を使い、注文後の製造指示書は確定済みの配置を読む。以下は従来の最小契約であり、統合DB案v4の `position_x/y/z`・`rotation_x/y/z`・色との対応、JSONの形式・版は実装前に同期する。

```text
placements
  id
  design_id
  part_id
  pos_x
  pos_y
  pos_z
  rot_y
  scale
  seq_no
```

- ③は3D表示と配置操作でこのデータを作る。
- ④は `pos_x` と `pos_z` を用いて俯瞰SVGを描く。
- ②は `seq_no` を飾り明細と対応付け、製造指示書に印刷する。
- ①は注文確定後も参照できるようDB整合性を保証する。
