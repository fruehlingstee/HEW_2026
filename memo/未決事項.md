## 1. データの役割とつながり

**中心となる担当：** ①が設計案を説明し、②が店舗業務、③が3D、④が買い手画面の観点で確認する。

**現在の扱い：** 注文前にdesignsを作り、placementsを紐づけ、ordersがdesignsを参照する方針は既存資料にある。詳細な関係・制約と4人の理解を揃える作業が残る。

### 何を問うているか

「何を保存するか」「どの表に保存するか」「別の表とどうつなげるか」「誰がどの情報を使うか」を確認する。テーブルとは同じ種類のデータを並べて保存する表、IDとは各データを識別する番号のこと。ER図は、その表同士の関係を表す図である。

### 1-1. デザインと注文の違い

デザインは「作成したケーキの内容」、注文は「そのケーキを購入する申し込み」である。ピンクのクリームに苺2個を置いて保存しただけならデザインだけが存在し、購入者名・受取日・支払いの状態を持つ注文はまだ作らない。

注文を作る際に対象のデザインを参照し、注文時の内容を固定する。編集途中のデータと製造対象のデータを混同すると、支払い開始後に見た目だけ変わる問題が起きる。注文後のロックと再注文は項目5で詳しく確認する。

確認すること：デザインだけの保存を許すこと、注文とデザインの対応、1つのデザインへの注文の一意性、再注文時に複製することを画面とDBの両方で扱えるか。

### 1-2. 飾り1個の位置をどこに保存するか

「苺という種類」はparts、「実際に左側へ置いた苺1個」はplacementsに保存する。同じ苺を2個置けば、パーツは同じものを参照し、配置は2件作る。

| 情報 | 保存の役割 |
|---|---|
| parts | 名前・現在の単価・モデル参照・種別など、飾りの基本情報 |
| designs | ケーキの色・メッセージなど、配置をまとめる親 |
| placements | design_id、part_id、位置・回転・倍率・配置番号・必要な配置色 |

配置にdesign_idがあることで、別のケーキの苺と混ざらない。part_idがあることで、同じ位置でも苺かブルーベリーか区別できる。所属店舗の違うパーツを参照させない条件も必要になる。

確認すること：③が作る配置データを①が保存でき、④がSVGに変換でき、②が製造指示書に使えるか。具体的な座標の意味は項目2で揃える。

### 1-3. 注文から製造指示書まで情報を取得できるか

店舗が注文を1件開いた際に、製造に必要な情報を漏れなく集められるかを確認する。

| 製造指示書で必要な内容 | 参照する情報の考え方 |
|---|---|
| 注文番号・受取日・購入者 | 注文データ |
| 注文時の色・メッセージ・名称・金額・アレルゲン | 注文時の控え（スナップショット） |
| 飾りの位置・向き・番号 | 注文に紐づくロック済みデザインの配置 |
| 現在の製造状況 | 注文状態 |

スナップショットとは、注文時点の値を控えとして保存すること。苺を200円で注文した後に現在価格を250円に変えても、過去の注文金額は変えない。名称・モデルの表示情報も同様に扱う。配置番号と明細の対応方法は明文化する必要がある。

確認すること：架空の注文を1件作ったつもりで「編集→注文→店舗一覧→詳細→指示書」をたどり、各画面に必要な情報の取得元を説明できるか。

### 1-4. 各テーブルの役割を1文で説明できるか

役割が曖昧な表は、担当によって違う意味で使われたり、情報の保存先が重複したりする。各候補に「この表は何を保存するか」を1文で付ける。

| テーブルの例 | 役割の説明 |
|---|---|
| stores | 店舗の基本情報・設定を保存する |
| parts | 店舗で使える飾りの基本情報を保存する |
| designs | 作成したケーキデザインを保持する |
| placements | デザイン上の飾り1個ごとの配置を保存する |
| orders | 購入申し込みと現在の注文状態を保存する |
| order_items | 注文時の明細・単価・数量を保存する |
| order_status_logs | 注文状態の変更履歴を保存する |
| payments / refunds | 決済・返金の処理と結果を保存する |

ordersの「今は製造中」と、order_status_logsの「いつ製造中になったか」は別の役割である。注文時の控えのような意図した重複保存は必要なので、重複を機械的に消すのではなく、目的と更新元を説明する。上表だけで完了にせず、ER図に登場する全候補を対象にする。

**完了の目安：** 全テーブルの役割、参照先、1対多などの関係、必須・任意の参照が説明でき、注文から指示書まで必要情報をたどれる。

## 2. 3D・SVG共通の座標

**中心となる担当：** ③④が座標と描画の案を出し、①が保存・検証、②が製造図の読みやすさを確認する。

**現在の扱い：** メートル単位、Yが上、上面中心を原点、Y軸回転のみとする案があるが、確定として扱わずレビューする。

### 何を問うているか

同じ配置データを3D画面、DB、俯瞰SVG、製造指示書で使ったとき、位置や向きが一致するかを問う。座標は「場所を数値で表す共通言語」であり、担当ごとに解釈が違うと、保存に成功していても別の位置に復元される。

### 細かく確認すること

| 論点 | 何を決めるか・決めないと起こること |
|---|---|
| 単位・実寸 | 1が1mなのか1cmなのか。案はメートルで5号直径0.15m。単位が違うとモデルの大きさが合わない |
| 原点 | ケーキの上面中心を基準にするか。土台底面の中心と混同すると飾りが浮く・埋まる |
| 軸・向き | Yを上、真上から12時を-Z、3時を+Xとする案を確認。SVGの画面座標へ変換する規則も揃える |
| 高さposY | 上面への配置高さをどう決めるか。自動固定か変更可能か、モデルの接地位置をどこに置くか |
| 回転 | rotYだけを許すか、XYZ回転が必要か。角度の保存単位はラジアンか。例：半回転はπラジアン |
| 倍率scale | 基準サイズと許容範囲。見た目だけ自由に拡大すると製造できない大きさになるため、商品として許す操作を決める |
| 範囲判定 | 中心点だけでなく、パーツの端までケーキ内に収めるか。苺の中心が内側でも端がはみ出す場合を考える |
| 配置番号 | seqNoを追加・削除時にどう扱うか。指示書の番号と同じ配置を指せるようにする |

GLBは3Dモデルを格納するファイル形式。③が書き出すモデルの原点・向き・実寸も、アプリ側と合わせる必要がある。

### 話し合いで使う具体例

苺を「中心・12時側・3時側」に1個ずつ置いたサンプルを用意する。3D表示、保存後の復元、SVGで同じ並びになるか説明する。端ぎりぎりの苺、倍率を変えた苺、回転した苺についても、許可・拒否を決める。

**完了の目安：** 単位・原点・軸・回転・倍率・配置範囲を一覧化し、③④が同じサンプルデータで位置を説明できる。実装後に行う一致検証の条件も残す。

## 3. 外周デコの操作仕様

**中心となる担当：** ③④が形と操作案を用意し、②が製造可能性、①が保存・検証条件を確認する。

**現在の扱い：** 外周デコの採用、あり・なし選択、約3種類の配置プリセット、自由配置・色変更は方針にある。形・プリセット内容・上限・配置制約は未決。

### 何を問うているか

利用者が「何を選べて、どこまで操作できるか」を決める項目。保存方法が決まっていても、操作ルールが曖昧だと、画面・3D・価格・製造指示で別の仕様になる。

### 細かく確認すること

| 論点 | 話し合う内容 |
|---|---|
| 形 | 絞りクリームなど、実際にどの形を作るか。モデル種類と製造時の表現が一致するか |
| プリセット | 約3種類の名前・配置・個数・初期色。画像または俯瞰図で説明できるようにする |
| 適用方法 | 既存デコを置き換えるか、追加するか。手作業で調整した配置を消す場合の確認表示 |
| 「なし」の動作 | 配置済みデコを全部消すのか。パレットを残すのか。画面表示と料金が一致するか |
| 上限 | 通常飾り12個に含めるか別枠か。デコ全体・種類別・色パレットの上限 |
| 配置範囲 | 外周だけに置けるか、上面の内側も許すか。ケーキからのはみ出しをどう防ぐか |
| 重なり | デコ同士、苺、メッセージプレートとの重なりを許すか。置けない場合の案内 |
| 色の操作 | 選択した1個・複数個・全体のどれを変更するか。パレット編集で既存配置が勝手に変わらないUIにする |
| 製造指示 | 色・個数・配置を店舗が読み取れるか。小さなデコが多数あるときの図と明細の表示 |

### 話し合いで使う具体例

白いデコのプリセットを適用し、2個だけ赤に変更した後、別のプリセットを選ぶ。このとき「赤い2個が残るか」「個数が増えるか」「料金がどう変わるか」を全員が同じように答えられるか確認する。

数値は会議で決める。説明用の例を、そのまま個数・上限の確定値として扱わない。

**完了の目安：** 各プリセットの図、操作ごとの結果、配置・個数・色数の制限を記載し、画面担当と3D担当が追加判断なしで実装できる。

## 5. 注文状態と編集できる期限

**中心となる担当：** ①②が状態遷移と操作権限を整理し、④が買い手導線、③がロック後の3D操作を確認する。

**現在の扱い：** 2026-09-28に、pending注文作成時の内容固定と期限切れ後の複製再注文を本チャットで採用。状態別の操作・画面表示・例外の詳細を揃える。

### 何を問うているか

いつケーキの内容を変更できなくし、その後は誰が何を操作できるかを問う。見た目の固定と注文の進捗は別に扱う必要がある。

### 注文状態を業務の言葉で確認する

| 状態 | 意味 | 確認する点 |
|---|---|---|
| pending | 支払待ち | 編集禁止、支払い再試行・期限の表示 |
| confirmed | 注文確定 | 通常注文は決済成功Webhookから遷移する |
| in_production | 製造中 | 店舗のどの操作で開始するか |
| ready | 受取可 | 通知・受取案内のタイミング |
| completed | 受取完了 | 店頭照合後に誰が完了操作するか |
| cancelled / rejected / expired | 取消・店舗却下・期限切れ | 遷移元、理由、返金との関係 |

Webhookとは、決済サービスからサーバーへ届く結果通知。通常注文では、買い手が成功画面を開いたことだけでconfirmedにしない。デモの例外は項目9で区別する。

### 固定する時点と内容

pending作成、注文時の控えの保存、仮確保との関連付け、デザインロックを同一トランザクションで行う。トランザクションとは、関連するDB更新を全部成功させるか全部取り消すかの単位である。注文だけ作られてデザインが編集可能のまま残る状態を防ぐ。

金額・色・メッセージ・表示情報などは注文時の控え、座標はロック済み配置を使う。決済成功時に現在のパーツ情報から作り直さない。

### 再試行・再注文で確認すること

有効な仮確保とpending注文がある間は同じ注文で支払いを再試行する。期限切れ・取消後や内容変更では元デザインを複製し、受取日と金額を再確認する。元のロックは解除しない。

例：支払い画面で「苺を追加したい」と戻った場合、元注文をどう扱い、どこから複製を始めるか。新しいデザインができても古い支払いが後から成功する可能性があるため、項目6とつなげて確認する。

**完了の目安：** 「現在の状態→操作する人→操作→次の状態→必要な通知・返金」を一覧化し、不正な飛び越しや二重操作の扱い、購入者への説明が決まっている。

## 6. 予約枠・決済の例外

**中心となる担当：** ①②が処理と復旧案を説明し、④が購入者への表示・再操作、③がデザインの扱いを確認する。

**現在の扱い：** 15分仮確保、店舗行ロック、1注文1PaymentIntent、期限後・取消後の成功決済は復活させず全額返金する方針を資料化済み。実装・競合テスト・4人レビューは別途必要。

### 何を問うているか

正常に1回で決済できる場合だけでなく、同時操作・期限切れ・通知遅延・通信失敗が起きても、過剰予約・二重請求処理・返金漏れにならないかを問う。

### 状況ごとに確認する

| 状況 | 採用方針・確認する結果 |
|---|---|
| 最後の1枠に2人が同時申込 | 仮確保できるのは1人だけ。取得失敗した側の画面と再選択を決める |
| 15分経過 | 仮確保を期限切れとして扱う。空き枠確認時にも解放し、定期処理だけに依存しない |
| 注文が製造中・受取完了になる | 状態が進んでも、その日の製造枠を使った事実は消えない |
| 期限後・取消後に決済成功通知 | 注文を復活させず全額返金。通知遅延でも処理時点の期限で判断する |
| 同じ通知が2回届く | 注文確定・枠・履歴・通知を重複させない |
| 通知処理の途中で失敗 | 受信記録があるだけで完了とみなさず、未処理分を再処理できる |
| 返金失敗 | 失敗・処理中などの状態を記録し、店舗から再実行できる |
| 外部の返金成功後にDB更新失敗 | 外部結果と照合して復旧し、同じ金額を再度返さない |

店舗行ロックとは、同じ店舗の枠を変更する処理をDB上で順番に進める仕組み。PaymentIntentはStripe上の支払いを管理する単位で、同じ注文では再利用する。冪等性とは、同じ要求を繰り返しても結果が二重にならない性質である。

### 4人が確認する範囲

①②は更新順序・重複防止・再処理方法を説明する。④は「決済成功に見えるが注文は期限切れで返金予定」などの表示を確認する。③は元デザインのロックと複製の扱いを確認する。全員がDBのロック構文を覚える必要はなく、各ケースで注文・枠・お金・画面がどうなるかを共有する。

**完了の目安：** 各ケースの期待結果と再対応者が決まり、同時実行・重複通知・返金復旧をテストできる条件として記録されている。

### 何を問うているか

### 権限を分けて考える

| 利用場面 | 確認する権限 |
|---|---|
| 作成者が未注文デザインを編集 | 作成者であることをサーバーでどう確認するか |

### 細かく決めること

shareIdとshare_token_hashなど資料で異なる呼び方を揃え、URLに出す値とDBに保存する値を区別する。共有期限はデザインの保持期間と整合させる。期限切れ・削除済み・存在しないURLで何を表示するかも決める。

PCでURLをコピーし、別ブラウザまたは別PCで開いて同じデザインを表示し、画像保存できることを確認する。QRによるスマホ導線は対象外。完成画像はサーバーへ保存しない。

### 具体例と完了の目安

## 8. データの削除・保持

**中心となる担当：** ①②が削除対象と履歴の保持を整理し、③④がモデル・共有・復元への影響を確認する。

**現在の扱い：** 未注文デザイン7日、注文済みデザインは受取日＋30日、個人情報の匿名化、財務履歴の分離保持という方針がある。参照中データの削除制約と処理順序は未確定。

### 何を問うているか

不要になったデータを消したとき、注文履歴や製造情報まで壊れないか。また、削除したつもりの個人情報が別の場所に残らないかを問う。

### 細かく確認すること

| 対象 | 決める内容 |
|---|---|
| 参照中のパーツ | デザイン・注文で使用中の場合に削除を拒否するか。過去のモデル表示をどう維持するか |
| 未注文デザイン | 7日の起算点、期限延長の有無、配置・パレット・共有情報の削除範囲 |
| 注文済みデザイン | 受取日＋30日の計算と削除対象。注文からの参照をどう扱うか |
| 仮確保 | デザイン・注文への参照が清掃を妨げないか。期限切れ記録をいつどう整理するか |
| 個人情報 | 氏名・電話・メールだけでなく、注文時の控え・メール記録・自由記述・ログも点検する |
| 注文・決済・返金履歴 | 個人情報から分離して何を残すか。保持期間の詳細が未決なら担当と期限を記録する |
| 共有画面・画像 | デザイン削除後は表示しない。端末に保存済みの画像とサーバーデータの削除を区別する |

外部キーは「参照先が実在することを守るDBの制約」。参照先を消すとき、削除を禁止するのか、一緒に子データを消すのか、参照だけ空にするのかを関係ごとに決める。まとめて削除する設定にすると、残すべき財務履歴まで消える可能性がある。

### 話し合いで使う具体例

受取日から30日を過ぎた注文を例に、「購入者情報とデザインは消すが金額・決済・返金記録は残る」状態を図にする。削除後に店舗画面で何が見え、何が見えなくなるかも決める。

登録済みパーツは常に利用可能という方針と、参照中パーツの削除制約は別問題。削除の代わりとして提供可否フラグを無断で復活させない。

**完了の目安：** データごとの期限・起算点・削除／匿名化／保持の方法、参照の扱い、処理順序、失敗時の再実行方法が整理されている。

## 9. 店舗・アレルゲン・デモに必要な情報

**中心となる担当：** ①②が保存項目と店舗運用を整理し、④が購入者表示、③がデモでの3D・リセットを確認する。

**現在の扱い：** 1店舗、ゲスト注文、店舗用の簡易セッション認証、最小限のアレルゲン表示、個人情報・決済・枠消費を省くデモという方針がある。保存項目・公開範囲・例外処理の具体化が必要。

### 何を問うているか

中心となるデザイン・注文だけ設計しても、店舗情報・原材料情報・ログイン・展示モードの保存先がなければ画面は完成しない。必要項目が揃い、公開してはいけない情報やデモデータが混ざらないかを確認する。

### 9-1. 店舗の基本情報・受付設定

店舗名・住所・電話・店舗注記のほか、最短何日後から受け取れるか、何日先まで注文できるか、締切時刻、曜日別・日別の製造枠を整理する。値の保存先、初期値、誰が変更できるか、変更済み予約にどう影響するかを決める。

受取日はJSTの暦日、保存日時はUTC、業務判定はAsia/Tokyoという共通ルールを確認する。日単位の予約枠という方針なので、資料画像に時刻があっても時間帯予約を追加しない。

### 9-2. 店舗ログイン

買い手用会員機能とは別に、店舗のログイン識別子・パスワードハッシュ・セッションの有効期間と失効を決める。ハッシュはパスワードをそのまま保存しないための値であり、公開画面へ返す情報ではない。

ログアウト後や期限切れの扱い、画面だけでなく保存・状態変更などの処理でも認証すること、他店舗データを参照できないことを確認する。デモ用店舗情報にも秘密の認証情報を混在させない。

### 9-3. アレルゲンと店舗注記

苺などの飾りだけでなく、土台・クリーム・メッセージプレートを含め、原材料情報をどこに登録して注文全体へ集約するかを決める。「原材料に含む」と「同一設備で扱う」の区別、重複表示の整理、店舗注記の保存先を確認する。

購入者が注文確認で見た内容と製造指示書の内容を一致させ、注文時の控えと確認時刻を残す。後から店舗登録を変えても過去の注文表示が勝手に変わらないようにする。除外フィルタや複雑な同意画面は現行範囲に含めない。

### 9-4. デモモード

デモ注文をis_demoなどで区別し、氏名・電話・メールの入力、Stripe決済、通常の予約枠消費を省く。必須項目がある通常注文と、個人情報を持たないデモ注文をDBでどう両立させるかを決める。

デモの番号採番、注文状態の進め方、リセット・展示終了後の削除範囲も必要。デモはサーバー側設定で有効化し、URLパラメータだけで通常注文をデモ扱いにできないようにする。集計や清掃で通常注文と混ざらないか確認する。

### 話し合いで使う具体例

店舗スタッフがログインして受取条件を変更し、購入者が原材料情報を確認して注文する通常経路と、展示PCで個人情報を入れずにデザイン・疑似注文・指示書まで見る経路を並べる。各画面に必要な値、その保存先、公開可否、デモで省く処理を書き出す。

**完了の目安：** 店舗設定・認証・アレルゲン・デモの項目一覧に、保存先・必須条件・公開範囲・変更権限が付いており、通常とデモのデータ処理を区別できる。
